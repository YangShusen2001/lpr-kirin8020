# 相机帧率排查记要：7 fps → 30 fps

**日期**：2026-09-21
**触发**：用户问「为啥帧率这么低啊，之前还能跑 25 帧」「相机只有 20 FPS 吗？能不能改进」
**结论**：两个独立缺陷叠加，都已修。生产档 **7 → 28 fps**，相机上限 **20 → 30 fps**。

本轮的方法论教训多于技术内容，所以按「试过什么 → 时间 → 结果」逐条记，包括
**三次被证伪的假设**和**两次我自己的读数错误** —— 这些是下一轮最该复用的部分。

---

## 一、结论先行

| 指标 | 修复前 | 修复后 | 倍数 |
|---|---|---|---|
| 生产档（det=CPU rec=NPU cls=CPU） | **7 fps** | **28 fps** | 4× |
| 基准档（只取帧，相机上限） | 20 fps | **30 fps** | 1.5× |
| `conv`（NV21→RGBA + rot90） | ~25 ms | **1.4–2.4 ms** | ~12× |
| native 单帧合计 | ~86 ms | ~20 ms | 4× |

两个根因：

1. **native 代码一直以 `-O0` 编译**（主因，占绝大部分差距）
   `-O3` 被 CMake 追加的 `-O0` 覆盖。详见 `build-mode-o0-regression.md`。
2. **相机自动帧率只到 20 fps，需显式请求 30**
   设备报 `[1-30, 60-60]`，但自动档停在 20；显式 `setFrameRate(30,30)` 后稳定 30.00。

## 三、两个根因

### 根因 A：`-O0`（见 `build-mode-o0-regression.md`）

`entry/build-profile.json5` 写了 `"cppFlags": "-O3"`，但 hvigor 默认 debug 构建，
CMake 追加 `-O0 -g` 在**其后**，编译器取最后一个 `-O`。真实编译行：

```
-fdata-sections ... -O3 -D__MUSL__ -O0 -g -fPIC
                   ^^^            ^^^
                   被废掉          实际生效
```

**无任何报错、警告、日志。** 唯一后果是全部 native 未优化运行。

### 根因 B：相机自动帧率不是上限

```
FPS RANGES analyze n=2 [1-30 60-60 ]
不设        → 20.00 fps
设 30-30    → 30.00 fps   ← 采用
设 60-60    → ~29.8 fps（active 报 60-60，传感器仍只给 30）
```

`WANT_HIGH_FPS` 原为 `false`，依据是旧笔记「自动档已最优，设 30 反而更慢」。
**那个结论是在 `-O0` 下测的**：当时流水线只有 7 fps，设不设帧率都到不了 30，
读数反映的是我们的处理速度，不是相机。修好优化后结论完全反转。

## 四、我犯的两次读数错误（最该记住的部分）

### 1. 把「上一档残留的窗口值」当成回调率

`GEAR_ARRIVE_ONLY`（callback 档）在自增 `totalArrived`/`arrivedInWin` **之前**
就 `return` 了，而那一档没有别的路径去更新它们。于是 UI 上显示的「到达 fps」
是**切换到该档之前**残留的值。我据此写下「callback = 20 fps」，并一度当成
「相机上限 = 20」的证据。

**教训**：一个「只数 X」的仪器，必须先确认它**真的在数 X**。
判据是日志里能看到它自己的计数在涨，而不是界面上有数字。

### 2. 以为「回调停摆」，其实是「没人结算」

`RATE` 行的打印逻辑只写在 `record()` 里，而 callback 档根本不调 `record()`。
所以那一档**永远不打 RATE**，看起来和「回调停摆」一模一样 —— 但应用活着、
无崩溃、其他 tag 日志正常（3820 行）。

**教训**：观测不到有两种原因 —— 现象没发生，或**观测代码没被执行**。
二者必须靠「这段代码有没有被调用」来区分，不能靠输出为空来推断。

**修法**：把窗口结算提成独立的 `billWindow()`，两条路径共用；
callback 档自增到达数后直接调它；RATE 行加 `gear=` 字段，
使读数**自带档位标签**，杜绝跨档误读。

## 五、被证伪的假设（价值不低于结论）

| 假设 | 检验方式 | 结果 |
|---|---|---|
| 首页探针抢占推理线程 | 全新启动抢测 | **证伪**：探针没跑仍 3.7 fps |
| `rot=90` 目标写入散射拖慢 conv | 主机微基准三变体 | **证伪**：只慢 4% |
| 16×16 分块能加速 rot90 | 同上 | **证伪**：反而慢 28% |
| 显示路与分析路互抢带宽 | 摘掉显示路复测 | **未获支持**：单路更糟（86 帧后停摆），已回退 |
| 相机上限就是 20 fps | 显式设 30-30 | **证伪**：得 30.00 fps |

**第 2、3 条尤其值得记**：微基准花了约 10 分钟，**阻止了一次无用的重写**。
当时的直觉（散射写）听起来很有道理，但代价实测只有 4%。
**在优化之前先量，比优化本身更省时间。**

**第 4 条的复测本身是混淆的**：单分析路下回调停摆，说明瓶颈不在带宽争用。
该实验只证明「摘掉显示路没好处」，**没有**证明「双路互抢不存在」——
后者的干净测法尚未设计出来，列为未决。

## 七、未决 / 下一步

1. **RQ4 的绝对延迟必须重测** —— T7 的 20 轮数据全部在 `-O0` 下采集，
   p50 139.5 ms 等绝对值含优化膨胀。方差结构（CPU 侧 CV 20.8% vs NPU 侧 13.2%）
   也需在 release 上重新确认。
2. **「双流互抢」仍是未决假设** —— 需要设计一个不引入停摆的干净测法。
3. **30 fps 仍受限于相机** —— 生产档 28/30，说明流水线已接近跟上；
   若要更高，需换分辨率或换传感器模式（`60-60` 区间拿不到 60，
   可能与 640×480 出流配置有关，未验证）。

   > **【2026-09-21 已定位，见 `camera-npu-headroom.md`】** 这一条当时问的是
   > 「生产档为什么到不了 30」，现在有答案了：**不是相机，也不是 NPU**。
   > 逐段拆开后，单帧 24–40 ms 里**检测段（在 CPU）占 17–20 ms，识别段（在 NPU）只占 3.3 ms**。
   > 而本文件 §一 记的 `infer 24–32 ms` 是**混桶**读数：检出帧与未检出帧混在一个
   > 滑动窗口里取中位数。分桶后（同一份归档日志）：
   > 未检出 infer p50 **20.30 ms**（n=92）vs 检出 **30.32 ms**（n=21）。
   > 也就是说「延迟 20–25 ms」与「有时 13 ms」不是抖动，是**条件不同**。
   > 同时发现：每轮开流后约 30 s 到达率崩到 1.4–5 fps 再爬回 30，
   > 而当时的 `WARMUP_FRAMES = 10`（≈0.33 s）完全没覆盖这段，所有旧读数都含爬坡期。
4. **`-O2` 下的落点/指纹不受影响已确认**，但**性能类结论**（T2 的
   加速比、T8 的延迟排序）都应标注构建模式后重核。
5. **本文件 §一 表格里的「生产档 28 fps」口径需附注** —— 它取自 `RATE arrive=`
   （唯一可称 fps 的量，口径正确），但**未分桶、未排除相机爬坡期**。
   重采数据见 `camera-npu-headroom.md`。

## 八、纪律（写给下一轮）

1. **量性能前先跑 `tools/check_native_build_flags.py`** —— 它不需要设备，
   直接读 `build.ninja` 的真实 FLAGS。`-O0` 的代价是 4 倍帧率。
2. **观测不到时，先问「观测代码有没有被执行」**，再问「现象有没有发生」。
3. **建仪器先验仪器**：让仪器报一个只有它能产生的、随时间变化的数，
   确认它真的在数目标事件，再拿它的读数下结论。
4. **「我记得测过」不等于「现在成立」** —— 旧结论若与构建配置或上游修复
   耦合，必须标注当时条件；本轮有 **4 条既有结论**因此作废。

# 续：帧率上限的三条路（见 camera-fps-ceiling.md）

本轮之后又测了三条路，**结论是能再提，但要换档位**：

| 方案 | 实测 | 结论 |
|---|---|---|
| **全 NPU 档（det/rec 都走 NNRT）** | **30.00 fps（±0.3，0 丢帧）** | ⚠️ 快但改变输出（「采用」已废止，见 camera-fps-ceiling.md 顶部更正块） |
| 降分辨率 640x480 -> 480x480 | ~27 fps | ❌ 证伪 |
| 请求 60 fps（任何分辨率） | ~27-29.8 fps | ❌ 证伪 |
| JS 取帧/异步并行化 | 最多省 7 ms/帧 | ❌ 收益小于换档 |

关键发现：**~30 fps 是相机侧硬上限，与分辨率无关**；
能否达到它取决于检测器放在哪里 ——
det 在 CPU 时 native 28.6 ms/帧（吃满 33.3 ms 预算）只能到 ~28 fps，
det 在 NPU 时 native 23.4 ms/帧（留 9.9 ms 余量）即稳定 30 fps。

**又一条「接口说 OK 但事实相反」**：`FPS SET active=60-60` 会被 API 接受并回报
成功，但传感器并不兑现（实测仍只给 ~30）。**必须实测到达率，不能信协商结果。**
这与 `-O0` 那次同类，已写入纪律第 5 条。

详见 `camera-fps-ceiling.md`。
