# 相机路的 NPU 余量：谁在吃帧预算

**日期**：2026-09-21
**触发**：用户问「NPU 好像基本能跑满了，刚改了 320×320？还能不能提高相机帧率？
我看延迟有 20~25 ms，那应该能到 40~50 帧？有时候延迟还能在 13 ms，是怎么回事？」
**结论**：**三个前提都要纠正**，然后问题才有解。

1. **320×320 不存在** —— 全 git 历史里 `ANALYZE_TARGET_W` 只有 640，真机预览档里也没有 320。
2. **「NPU 跑满了」不可测** —— 硬约束，本项目禁止任何利用率数字（ADR-0003）。
3. **20–25 ms → 40–50 帧是算术用错了量** —— `1000/p50` 是服务时间倒数，不是 fps；
   相机侧上限实测 **~30 fps**，40–50 帧在这条路上不可达。

而「20–25 ms」与「13 ms」的差别**不是抖动，是条件不同**：一个是生产档未检出，
一个是全 NPU 档未检出。分桶后一切都对上了。

**真正的答案**：生产档在有车牌时 **frame p50 = 40 ms > 33.3 ms 预算（余量 −6.7 ms）**，
所以到不了 30 fps。而**吃预算的是 CPU 上的检测段（19.6 ms），不是 NPU 上的识别段（4.0 ms）**。
「榨干 NPU」在这条流水线上已经不是瓶颈了 —— 继续压 NPU 收益极小。

---

## 一、被纠正的三个前提

### 1.1 「刚改了 320×320」——不存在

| 检查 | 结果 |
|---|---|
| `ANALYZE_TARGET_W` 全部 git 历史 | **只有 640**，从未出现 320 |
| 真机预览档列表（`PROFILES[0]`，24 档） | 480x480 / 640x480 / 720x720 … **没有 320 宽的档** |
| 真机 `STREAM START` | `show=960x960 analyze=640x480 rot=90` |
| native 回传 | `wh=480x640`（rot=90 后宽高互换） |

你记的 320 是**检测器自己的输入边长**：`MODEL_DET = models/y5fu_320x_head_fp32.ms`，
`inputShape=[1,320,320,3]`，native 侧 `LprSessions::detSize = 320`
（`lpr_pipeline.h:105` 声明、`napi_init.cpp:824` 默认构造，**没有参数能传**）。自 T1 起未变。

### 1.2 「NPU 基本跑满了」——不可测，且是硬约束

ADR-0003 与 `AGENTS.md` 硬约束 1：NPU 利用率**物理上不可读** —— 应用侧不行，`hdc` 侧也不行
（DevEco Profiler / SP_daemon / hiperf 对 NPU 都没有负载计数器；SP_daemon 只有 `npu_thermal`，
那是**温度**不是负载）。**本笔记不产出任何利用率数字。**

替代证据形态（本项目唯一允许的）：**延迟余量 + 逐算子落点 + 张量指纹**。

### 1.3 「20–25 ms → 40–50 帧」——算术用错了量

`1000 / p50(frameMs)` 是**服务时间的倒数**，不是 fps。`CONTEXT.md` 把
「服务时间 / 到达率 / 完成率」定义为三个量，**只有后两者可以对外称 fps**。

相机侧硬上限由两个独立档位同时锚定：

| 档位 | 说明 | 实测到达率 |
|---|---|---|
| 基准档（gear 3） | 只取帧，不推理 | **29.99 fps**（26.93–30.18，50 窗口，0 丢帧） |
| callback 档（gear 4） | 只数回调，连帧都不取 | **≈30.0 fps**（26 窗口） |

所以相机路的天花板就是 ~30 fps；40–50 帧不可达。
但 **20–25 ms 这个数本身有意义** —— 它是每帧成本，余量 = `33.3 − frameMs`。

> ⚠️ **【2026-09-21 更正】本段「天花板就是 ~30 fps；40–50 帧不可达」已作废。**
> 那两个数是 `NORMAL_PHOTO` 会话下「只取帧」档的读数。换 `NORMAL_VIDEO` 会话
> + 一条固定 `60-60` 的 `VideoOutput` 后，同为「只取帧不推理」的实测是
> **49.98 fps**（42.74–57.94，n=43）。详见
> `camera-60fps-alternatives-research.md` 第四节与 `t9-60fps-inference-throughput.md`。
> 「40–50 帧不可达」在**流水线**意义上仍成立（有车牌时全 NPU 约 44 fps），
> 但理由要从「相机给不了」改成「流水线吃不下、并把相机背压回来」。

## 二、核心：13 ms 与 20–25 ms 是两个不同条件

同一份归档日志（`evidence/t3_camera_30fps_release.log`）按 `count` 分桶：

| 档位 | 未检出（count=0） | 检出（count>0） |
|---|---|---|
| 生产档 infer p50 | **20.30 ms**（n=92） | **30.32 ms**（n=21，max 140） |
| 全 NPU infer p50 | **13.64 ms**（n=27） | 33.14 ms（n=1，样本不足） |

即：**13 ms ≈ 全 NPU + 未检出**，**20–25 ms ≈ 生产档 + 未检出**。

**为什么界面读不出来**：`record()` 把**所有帧**塞进同一个滑窗取 p50，
而检出帧要多跑矫正 + 识别 + CTC + 判色。混桶得到的是两种分布的混合物。
`STAGE` 行每 30 帧才打一条，正好是混合后的抽样。

**修法**：`infer`/`conv` 桶按 `count > 0` 拆开；`frameMs` 不分桶（吞吐关心每帧实际墙钟）。

## 三、复采结果：生产档余量为负，瓶颈在 CPU 检测段

**协议**（`tools/run_camera_sweep.ps1`，档位由 `uitest uiInput click` 外部驱动）：

| 项 | 值 |
|---|---|
| 稳态门 | 开流后 **45 s** 不计入统计（相机爬坡） |
| 每档观测 | 60–90 s |
| 分析路 | 640×480（rot=90） |
| 构建 | release（`-O2`，已过 `check_native_build_flags.py`） |
| 热档 | 4（电池 43 ℃）—— **跨轮比较只在同热档内做** |

### 3.1 逐档余量表

| 档位 | 到达 fps | 未检出 frame p50 | 检出 frame p50 | 检出余量 vs 33.3 ms |
|---|---|---|---|---|
| **生产**（det=CPU rec=NPU） | 24.79（20.62–28.63） | 30.0 ms | **40.0 ms** | **−6.7 ms（超预算）** |
| **全 NPU**（det/rec=NNRT） | **29.96**（26.30–30.42） | 21.5 ms | 28.0 ms | **+5.3 ms** |
| 基准（只取帧） | 29.99 | — | — | 相机上限 |

**读法**：生产档在**有车牌**时每帧要 40 ms，而相机只给 33.3 ms —— 我们比相机慢，
所以到达率被拖到 24.8 fps。全 NPU 档把检出帧压到 28 ms，才有 5.3 ms 余量贴住 30 fps。

> ⚠️ **【2026-09-21 口径更正，见 `t9-60fps-inference-throughput.md` 纪律 14】**
> 本表「到达 fps」一列**是在 30 fps 供给（NORMAL_PHOTO）下测的**，那一档产能
> （全 NPU ~32 fps）≥ 供给（30），**无背压**，所以这些数仍然有效。
>
> 但**读法那句「我们比相机慢，所以到达率被拖到 24.8 fps」的推理方式不成立**：
> 生产档检出帧 40 ms → 产能 25 fps，而相机供给 30，此时**确实**是流水线更慢、
> 到达被背压拖下来 —— 结论对，但**不能**再用 `arrive` 单独证明它。
> `arrive == done` 与 `dropped == 0` 在背压下同样出现（被顶掉的帧从未投递，
> 不计入 dropped）。判据只能是与「只取帧」档对照。
>
> 在 60fps 供给下这会更明显：gear 6（只取帧）49.98 fps，而 gear 7/8（开推理）
> 只有 36.18 / 43.55 —— 后两列的 `arrive` **不是相机供给，是流水线产能**。

### 3.2 谁在吃预算：CPU 检测段 19.6 ms vs NPU 识别段 4.0 ms

检出帧的完整账（`sweep1` gear=0，`STAGE` 的 `stages=` 字段 n=81；全部为 **native 侧**）：

| 段 | 落点 | p50 | 占 frame 40 ms 的比例 |
|---|---|---|---|
| JS prep（取帧 + 组件拷贝） | JS | 1.00 ms | 2.5% |
| **native conv**（NV21→RGBA **+ 1.2 MB rgbaSum 校验和**） | CPU | **7.15 ms** | 17.9% |
| **检测段（detect 合计）** | **CPU** | **19.61 ms** | **49.0%** |
| ├ letterbox | CPU | 2.49 ms | |
| ├ encode + infer（det 前向） | **CPU** | **15.59 ms** | |
| └ decode + NMS | CPU | 0.03 ms | |
| rectify（透视矫正） | CPU | 0.49 ms | 1.2% |
| **识别段（recog）** | **NPU** | **3.98 ms** | **10.0%** |
| cls（判色，像素测量） | CPU | 0.08 ms | 0.2% |
| NAPI + 调度 + 残差 | — | ~7.7 ms | 19.2% |
| **合计 frame** | | **40.00 ms** | 100% |

> ⚠️ **口径警告（我在这张表上先错过一次）**：`STAGE` 行的 `conv=` / `infer=` 是 **native 侧**的值；
> `RATE` 行的桶是 **JS 侧**的值（`prep` = JS 取帧拷贝，`rt` = JS↔native 整段往返）。
> 两者**不是同一个量**：`rt`(39.0) ≠ native `infer`(25.6)，差的就是 native conv + NAPI。
> 早先我把 native `conv` 当成「JS prep」写进表里（7.15 被标成 JS 侧），是错的 ——
> 真实 JS prep 只有 **1.00 ms**。字段已改名（见 §6.2），但读旧数据时仍要看清是哪一侧。

**这就是本轮最重要的结论**：**检测段（CPU）比识别段（NPU）贵 5 倍。**
「榨干 NPU」在这条流水线上**已经不是主要矛盾** —— 识别段只占 3.98 ms（10%），
即便把它压到 0，也救不回生产档那 −6.7 ms 的缺口。

### 3.2b 复采复现性（`sweep2`，热档 3）

| 段 | sweep1（热档 4） | sweep2（热档 3） |
|---|---|---|
| JS prep | 1.00 | 1.00 |
| native conv | 7.15 | 7.32 |
| 检测段 | 19.61 | 23.75 |
| 识别段（NPU） | 3.98 | 3.75 |
| frame（检出） | 40.00 | 36.00 |
| 到达 fps | 24.79 | 26.45 |

方向一致：**检测段是最大项，识别段恒定 ~4 ms**。绝对值的差主要来自热档
（sweep1 热档 4 / 43 ℃，sweep2 热档 3 / 41 ℃）—— 这正说明**跨热档不可直接比**。
识别段在热档 3→4 之间只动 0.23 ms，**进一步佐证它不在关键路径上**。

> ⚠️ **一处未解释的残差，记在这里而不是抹平**：
> 两轮的「native 分段之和」与「RATE frame」对不齐的程度**不同**：
>
> | | native 分段之和 | RATE frame | 残差（NAPI/调度等） |
> |---|---|---|---|
> | sweep1（热档 4） | 1.00+7.15+19.61+0.49+3.98+0.08 = 32.31 | 40.00 | **+7.69** |
> | sweep2（热档 3） | 1.00+7.32+23.75+0.61+3.75+0.13 = 36.56 | 36.00 | **−0.56** |
>
> sweep2 的分段几乎**完全解释了** frame，sweep1 却多出 7.7 ms。
> 可能原因（**未验证**）：`STAGE` 每 30 帧才抽样一条，两轮抽样条数不同
> （sweep1 n=81 / sweep2 n=45），且 `STAGE` 与 `RATE` 的**统计窗口不对齐** ——
> `STAGE` 是抽样点，`RATE` 是 2 s 滑窗，两者覆盖的时间段不重合时，
> 「分段之和 ≈ frame」这个恒等式就不成立。
> **这不影响主结论**（检测段 ≫ 识别段，两轮一致），
> 但说明**逐段绝对值目前不能当作精确分解**，只能当作量级判断。
> 要拿到精确分解，得让 `STAGE` 与 `RATE` 共用同一批样本（登记为后续改进）。

### 3.2c 【新发现，2026-09-21】检测段在流水线内比**隔离基准慢 2 倍**

这一条是做完 §5.2 的 C4（CPU 线程扫描）后掉出来的，**它比 C4 本身重要得多**。

跑 `Index.ets::threadSweep()`（3 模型 × `cpu_t{1,2,4,6,8}`，warmup 5 + 30 次 p50），
同一份 `y5fu_320x_head_fp32.ms`、同一后端 `cpu`、同样 4 线程：

| 口径 | 位置 | p50 | p50Io（memcpy+推理） |
|---|---|---|---|
| **隔离基准**（探针页，无相机流） | `OH_AI_ModelPredict` | **7.42 / 7.49 ms**（两次） | **7.94 / 8.00 ms** |
| **流水线内**（相机页 sweep1，热档 4） | `tInferMs` | **15.26 ms** | — |
| **流水线内**（相机页 sweep2，热档 3） | `tInferMs` | **19.51 ms** | — |

**流水线内慢 1.9× ~ 2.4×。** 且注意方向：**热档更低的 sweep2（3 / 41 ℃）反而更慢**
（19.51 vs 15.26）—— 所以**主因不是热降频**。

**已排除的解释**：

| 解释 | 为什么不成立 |
|---|---|
| 不同模型 | 两侧都是 `y5fu_320x_head_fp32.ms`（`MODELS_FULL[0]` == `MODEL_DET`） |
| 不同后端/线程 | 两侧都解析到 CPU + 4 线程；都设 `PERFORMANCE_HIGH` |
| 热降频 | 更热的 sweep1 反而更快（15.26 < 19.51） |
| 输入编码（pack） | `tPackMs` 只有 **0.49 ms**，且已单独计时，不在 `tInferMs` 里 |
| 输出拷贝 | 隔离侧的 `p50Io` **已把 memcpy 进出口算进去**，仍是 8.00 ms |
| 测量抖动 | 两次独立扫描 7.487 / 7.420 ms，`L2` **逐位相同**（1042.6634），极稳定 |

**尚未验证的假设（按可能性排序）**：

1. **DVFS / 频率档**：隔离探针是**紧循环**（30 次连发），CPU 频率被拉满；
   流水线是**每帧一次**（间隔 ~33–40 ms），中间夹着相机回调、NAPI、NPU 调用，
   可能长期停在较低频点。**这是最可能的原因**，也最符合「更热的 sweep1 反而更快」
   （热时系统更倾向保持性能档）。
2. **线程争用**：相机/ISP/显示路本身占核，det 的 4 个工作线程拿不满。
3. **缓存污染**：每帧在 RGBA 缓冲（1.2 MB）、letterbox 输出、det 输入之间来回，
   L2/L3 命中率低于紧循环。

**为什么这条比 C4 重要**：如果 2 倍差距主要来自 DVFS/调度，那么
**「把检测段从 19.6 ms 优化到 12 ms」这个目标里，有一半以上不在算子本身** ——
在**我们无法控制的调度行为**里。

#### 3.2c.1 已做的三个实验（两个否定，一个未决）

**实验 1：CPU 线程扫描（C4）—— 否定，默认值已是最优。**

`Index.ets::threadSweep()`，`y5fu_320x_head_fp32.ms` × `cpu_t{1,2,4,6,8}`：

| 线程档 | p50 | p50Io |
|---|---|---|
| `cpu_t1` | 12.69 | 12.69 |
| `cpu_t2` | 11.72 | 12.15 |
| **`cpu_t4`（当前默认）** | **7.49** | **8.00** |
| `cpu_t6` | 9.93 | 10.50 |
| `cpu_t8` | 9.25 | 9.89 |

两次独立扫描复现（7.487 / 7.420 ms，`L2` 逐位相同 1042.6634）。
**t4 已是最优，且 t6/t8 反而更差** —— 说明 4 线程正好吃满可用的大核并行度，
再多只是争用。**C4 因此关闭：无收益，不改产品配置。**

**实验 2：CPU 亲和扫描 —— 否定，且方向反直觉。**

新增 `cpu_a{N}` 档（`OH_AI_ContextSetThreadAffinityMode`，此前**从未调用**），
线程数固定 4：

| 模型 | `cpu_t4` 无绑定 | `cpu_a1` 大核优先 | `cpu_a2` 小核优先 |
|---|---|---|---|
| `y5fu_320x`（det） | **7.67** | 11.36 | **19.45** |
| `rpv3`（rec） | **8.85** | 14.86 | 22.56 |
| `litemodel_cls`（cls） | **1.06** | 20.00 | 1.25 |

- **无绑定最快**；大核优先反而慢 48%，小核优先慢 154%。
- 三者 `L2` **逐位相同** ⇒ 无串扰，纯计时差异。
- **`cpu_a2` 的 19.45 ms 与流水线内的 19.51 ms 几乎相同** —— 这是本轮最耐人寻味
  的巧合：它提示流水线里的 det **可能等效于「被挤到小核」的状态**。
- **注意**：`cpu_a1` 在隔离基准里也比无绑定慢（11.36 vs 7.67）。所以
  「绑大核更快」在本设备上**不成立**（Kirin 8020 的簇划分与 `mode` 语义未必
  与直觉对应，或绑定会剥夺引擎跨簇调度的自由度）。

**实验 3：把 `cpu_a1` 装进相机路径实跑 —— 否定，且更慢。**

把 `DET_CPU_BACKEND` 设为 `'cpu_a1'` 重新构建，跑完整相机协议
（`evidence/camera_aff1.log`，47 稳态窗口，检出 1410 帧）。落点自证确认生效：
`det LANDED=CPU:t4a1 (req=cpu_a1)`。结果：

| 轮次 | 热档 | `tDetect` p50 | `tInfer` p50 |
|---|---|---|---|
| sweep1（无绑定） | 3–4 | 19.61 | 15.26 |
| sweep2（无绑定） | 3 | 23.75 | 19.51 |
| **aff1（`cpu_a1`）** | **1–2**（更凉） | **35.61** | **29.55** |

**在更凉的热档下反而慢了 1.5–1.9 倍。** 这同时说明两件事：
① 亲和绑定**帮不上**，无绑定就是最优（已改回 `'cpu'`）；
② **热档不是主因** —— 热档 1–2 比热档 3–4 慢得多，方向完全相反。

**未决**：2 倍差距的成因仍未定位。已排除热降频、线程数、亲和绑定、输入打包
（0.49 ms）、输出拷贝（`p50Io` 已含）。剩余最可能是 **DVFS 频率档随调用
疏密变化**，但 `scaling_cur_freq` / `thermal_zone` 在真机上 **`Permission denied`**，
应用侧也没有读频接口 —— **该假设目前无法直接验证**。
登记为开放问题，见 §5.2 的 C8。

> ⚠️ **一处必须说明的实验局限**：`aff1` 的**热档（1–2）与 sweep1/sweep2（3–4）
> 不同**，所以严格说这三行**不满足「同热档内比较」的纪律**。但正因为方向相反
> （更凉却更慢），它作为「热档不是主因」的证据是**成立的**；
> 而作为「cpu_a1 比无绑定慢」的证据则**不严谨** —— 后者只由**隔离基准**
> （同一热档下三者同场测得，实验 2）严格支持。两处结论的证据强度不同，不要混用。

#### 3.2c.2 【已定位】C8 的成因是**两个叠加的机理**

上面那段「未决」写于 3.2c.1 之后。**随后用自建探针把它定位了** ——
不是靠猜，是靠一个**剂量-反应 + 忙等对照 + 线程数对照**的三步实验。

**探针**：`benchAsync` 新增三个**在计时区之外**起作用的参数
（`ms_engine.cpp::MsBenchRun`）。它们只改变「这次推理是在什么状态下被调用」，
被计时的那次 `OH_AI_ModelPredict` 本身与历史基线逐位相同：

| 参数 | 作用 | 检验的假设 |
|---|---|---|
| `gapMs` | 迭代间 **sleep** | 调用变稀疏是否变慢 |
| `spinMs` | 迭代间**忙等**（时间相同，但 CPU 不空闲） | 分离 DVFS 与「时间本身」 |
| `polluteKB` | 迭代间搬运干扰缓冲 | 缓存/内存带宽污染 |

自证：`min < gapMs`（实测 `min=7.06 < 33`）证明 sleep 确实在**计时区之外**。

**第一步：剂量-反应（`cpu_t4`，`y5fu_320x`）**

| `gapMs` | 0 | 8 | 33 |
|---|---|---|---|
| p50 | **7.26** | 16.14 | **31.56** |

> ⚠️ **2026-09-21 更正**：本表原先列了 5 档（`0 / 4 / 8 / 16 / 33`），
> 值写作 `7.41 / 9.16 / 16.33 / 24.16 / 30.74`。
> **逐条回查 `evidence/camera_gap_sweep.log`（63 行）后确认：
> 该扫描只跑过 0 / 8 / 33 三档，`4` 与 `16` 从未测过；
> 且三个真实值也与原表不符。** 原表那 5 个数在 evidence 里搜到的命中
> 全是无关数字的巧合（`infer=17.4198`、`ms_cpu=16.334`、`stages=24.1656|…`、
> `arrive=30.74`），**没有一个是 gapMs 档的 p50**。
> 上表已按 `camera_gap_sweep.log` 的 `MATRIX … LANDED=CPU:t4 gapMs=…` 行重写。
> 结论方向（单调、跨度约 4 倍）不变 —— 7.26 → 16.14 → 31.56 仍是 4.3 倍，
> 且 33 ms 档仍落进流水线观测区间。**但「4 档」「16 档」的说法必须删除。**
>

单调、跨度 4.3 倍，**且 33 ms 档正好落进流水线观测到的 15–31 ms 区间**。
污染档（`polluteKB=1200`，≈ conv 的 1.2 MB RGBA 写）**毫无影响**（7.50 vs 7.26）
⇒ **缓存/带宽假设被否掉**。

> 这一步同时**推翻了代码里的一条旧结论**：`ms_engine.cpp:684-687` 曾记
> 「sleep 3 ms 只把 p50 从 7.54 推到 8.71 ms，所以负载节奏解释证据薄弱」。
> **那是剂量太小**（3 ms 落在曲线的第一段，斜率尚未起来）。用 8/16/33 ms 重做，
> 效应非常清楚。**「不显著」有时只是「剂量不够」** —— 这条已就地更正。

**第二步：忙等对照（关键一刀）**

| 档（`cpu_t4`） | p50 | vs 基线 |
|---|---|---|
| 紧循环 | 7.26 | — |
| `gapMs=33` | 31.56 | **+24.30** |
| **`spinMs=33`（忙等）** | **28.06** | **+20.80** ← **几乎没救回来** |

若纯是 DVFS，忙等应把频率顶住、p50 回到 ~7 ms。**它没有** ⇒
**DVFS 不足以解释**（至少对 4 线程而言）。

**第三步：线程数对照（定位到第二个机理）**

把同一组档在 **`cpu_t1`（单线程，无线程池可 park）** 上重跑：

| 档 | `cpu_t4` | `cpu_t1` |
|---|---|---|
| 紧循环 | 7.26 | 12.37 |
| `gapMs=8` | 16.14 | 23.18 |
| `gapMs=33` | 31.56 | 39.20 |
| **`spinMs=33`** | **28.06**（+20.80） | **12.66**（**+0.29**） |
| 污染 1.2 MB | 7.50 | 12.42 |

**`cpu_t1` 上忙等把效应几乎完全消除（+26.83 → +0.29 ms）**，而 `cpu_t4` 上不能。

**结论：C8 是两个机理叠加**

1. **DVFS / 频率** —— 由 `t1` 上「忙等完全消除效应」确证。
   调用变稀疏时 CPU 降频，推理跑在低频。这是**主因**，且**在任何线程数下都存在**
   （`t1` 的 +26.83 与 `t4` 的 +24.30 同量级）。
2. **线程池唤醒延迟** —— 由「`t4` 上忙等救不回来」确证。
   `t1` 没有工作线程可 park，所以忙等（占用调用线程）就够；
   `t4` 的另外 3 个工作线程**仍然闲置并 park**，忙等**碰不到它们**，
   下次 predict 要先把它们唤醒，这段开销落在计时区内。
   → `t4` 上忙等后仍残留 **+20.80 ms**，`t1` 上只剩 **+0.29 ms**。

> 这个分解解释了此前所有看似矛盾的观测：
> - 「更热的一轮反而更快」：热时系统更倾向保持高频 ⇒ 机理 1 被削弱。
> - 「紧循环快、流水线慢」：流水线每帧间隔 ~33 ms，**同时**踩中机理 1 与 2。
> - 「忙等也慢」：忙等只占住调用线程，**碰不到线程池里的其他线程**。

**对 C8 的处理**：机理 1（DVFS）**在应用层不可控**（无读频/锁频接口，
`Permission denied`）。机理 2（线程池唤醒）**理论上有解** —— 但代价是
**常驻忙等线程**，违反 `AGENTS.md` 硬约束 6（持续后台计算不被允许），
且会与相机抢核。**故本轮不实现**，登记为「已知且不可控」。
**实践含义**：不要把隔离基准的 7.4 ms 当作产品路径可达的下限 ——
在「每帧一次」的调用节奏下，该模型的实际成本就是 ~15–31 ms。

**交叉验算（一个有用的定量自洽）**：`gapMs=33` 的纯空闲预测是 **31.56 ms**，
但流水线实测只有 **15.26（sweep1）/ 19.51（sweep2）ms** —— **比纯空闲预测快 1.6–2 倍**。
这不矛盾，反而**印证了机理 1 的解释**：`gapMs=33` 档里 CPU **完全空闲**（纯 sleep），
而流水线那 33 ms 里 CPU 一直在干活（conv 7.2 ms + letterbox 2.5 ms + NAPI + NPU 调用），
**频率没有被拉到最低**。也就是说：

> **流水线的真实成本落在「紧循环 7.4 ms」与「纯空闲 31.6 ms」之间，
> 具体位置取决于帧内 CPU 有多忙。**

这给了一个**可检验的推论**（未验证）：若在帧间插入**无意义的 CPU 忙活**
（例如把 conv 提前、或让 JS 侧做点计算），理论上能把 det 拉回曲线左端 ——
但那只是**把开销从 det 挪到别处**，端到端不会变快，且同样违反硬约束 6。
**故仅作记录，不作为优化方向。**



⚠️ **本发现不改变 §3.2 的主结论**（检测段 ≫ 识别段），但它**修正了绝对值的可解释性**：
「检测段 19.61 ms」是**流水线内**的值，不能与论文里任何**隔离基准**的 CPU 数字直接比。

### 3.3 全 NPU 档为什么能到 30：它省的是检测段

全 NPU 档把检测段从 CPU 挪到 NPU，检出帧 40.0 → 28.0 ms。但**这一档读错参考图**
（`det-backend-alters-result.md`：`cropSum` 2773473 → 2763123，`D` 被读成 `0`）。
**所以它不是可用的提速手段，只能用于性能上限测量。**

### 4.1 `setFrameRate` 有**重复调用**约束（直接影响我们的切档）

`camera-framerate.md:98-99` 与 `camera-setframerate-native.md:116-117` 明确：

> * 设置**非固定**帧率后，**不支持再次调用**该接口重新设置动态帧率。
> * 设置**固定**帧率后，支持重新设置固定帧率，但**必须保证新设置的帧率可以整除
>   之前设置的帧率或者被之前设置的帧率整除**。

从而把「热致掉帧」从「不明抖动」变成「可标注的条件」。

## 五、回答「还能不能提高相机帧率」

分两问，答案不同：

### 5.1 相机侧：不能。~30 fps 是硬上限

- 基准档 29.99 fps、callback 档 ≈30.0 fps —— 两个独立档位互证。
- 请求 60 fps 不被兑现（`camera-60fps-research.md` 已给源码级根因：
  框架零校验零复查，钳位在厂商闭源 daemon 的 `setMaxFps()`）。
- 降分辨率换不到帧率（`camera-fps-ceiling.md` 已证伪）。

> ⚠️ **【2026-09-21 已推翻，见 `camera-60fps-alternatives-research.md` 第四节】**
> 本节标题「~30 fps 是硬上限」以及上表「相机路的天花板就是 ~30 fps」**均已作废**。
> 实测：在 `NORMAL_VIDEO` 会话里加一条固定 `60-60` 的 `VideoOutput`，
> **只取帧不推理**时分析流到达率可达 **49.98 fps**（42.74–57.94，n=43，热档 3）。
> 即 30 fps 不是传感器硬上限，而是「预览/分析-only 配置」下的钳位值。
>
> **但推翻的只是「相机能不能给」，不是「流水线能不能用」。**
> 同一 60fps 配置下一旦开推理，到达率会被**背压**回产能：
> 生产档 36.18、全 NPU 43.55 fps（详见 `t9-60fps-inference-throughput.md`）。
> 所以对本节的结论应改述为：**相机侧可供给 ~50 fps，但流水线实际只能消耗
> ~32（生产）/ ~45（全 NPU）fps**，瓶颈仍在检测段。
>
> ⚠️ 另注：上面「基准档 29.99 / callback ≈30.0」这两个数本身**没错**，
> 但它们是「只取帧」档在 **NORMAL_PHOTO** 会话下的读数；NORMAL_VIDEO + VideoOutput
> 是另一套配置，不可互相代入。

>
> **C3 的修正说明**：初稿估「去掉校验和能省 1~3 ms」，也是错的。
> 校验和已经优化过：`napi_init.cpp:862-878` 记录了主机微基准
> **0.6903 ms → 0.1642 ms（快 4.2x，逐位相等）**，且注释明确禁止改成抽稀采样
> （会漏检单字节改动，毁掉它作为等价性证据的价值）。
> 即**它现在只值 0.16 ms**，而 native conv 总计 7.15 ms —— 说明 conv 的 7 ms
> **几乎全是 NV21→RGBA 的逐像素整数运算本身**（`lpr_pipeline.cpp:1234-1259`，
> 30 万像素 × 每像素 3 次乘法 + 3 次 clamp + 旋转坐标计算），
> 不是校验和。**要省 conv 只能动那段像素循环（C2），不是动校验和。**

**C1–C3、C6、C7 都不碰「识别段」**。这正是本轮方法学的落点：**「榨干 NPU」问错了对象** ——
在这条流水线上，NPU 那一段（3.98 ms）已经便宜到不值得再压。

**而 C8（2 倍差距）是唯一有可能一次性覆盖 −6.7 ms 缺口的候选**，也是唯一
**可能完全不在算子层面**的候选 —— 值得优先于 C1/C2 去查。

## 六、附带修掉的两个仪器缺陷（都不改产品行为）

### 6.1 callback 档（gear 4）**从未成功运行过**

原实现「不 `readLatestImage`，不 `release`，只数回调」—— 听起来合理，实际是错的：
接收器只有 8 格，30 fps 下 ~0.27 s 填满，相机随即**停止回调** `imageArrival`。
于是这一档测到的不是「相机能回调多快」，而是「缓冲填满用了几帧」。

**证据**：全部归档日志里**没有任何 `gear=4` 行**；本轮首次运行时
12 s + 45 s + 90 s 全程 **0 个 RATE 窗口**，同时 `all buffer are using` 持续刷屏。

**修法**：照常 `readLatestImage` + `release`（只为腾空缓冲），不推理、不计延迟统计。
到达计数在抽帧**之前**已经记过，所以「数回调」的目的不受影响。
修复后实测：26 个窗口，`arrive≈30.0 / done=0`（正确签名：只数到达，不完成）。

### 6.2 字段名歧义：`infer_*` 实际是「往返」，不是 native `infer`

`record()` 拿到的是 `cameraFrameAsync` 的**整段往返**（NAPI + native conv + 流水线），
而 `STAGE` 行的 `infer=` 是 **native 侧**的纯流水线耗时。两者**不是同一个量**，
但早先都叫 `infer` —— 同一批数据里 `infer_hit_p50=39` 与 `STAGE infer p50=25.58` 并存，
看着像自相矛盾。

**修法**：桶字段改名 `rt_*`（round-trip）与 `prep_*`（JS 侧），
与 `STAGE` 的 native `conv=`/`infer=` 明确区分。**名字必须自带口径。**

## 七、采集纪律（写给下一轮）

1. **稳态门必须过**。开流后 ~30 s 到达率崩到 1.4–5 fps 再爬回 30
   （相机 daemon `setMaxFps mCurMaxFps=0 -> 27`，切档后才 `27 -> 30`）。
   `WARMUP_FRAMES = 10`（≈0.33 s）**完全不够**；现用 `SETTLE_MS = 45000`。
   未过门的读数会把 1.4 fps 的窗口算进「稳态」。
2. **必须分桶**。检出 / 未检出的 `infer` 差一倍以上，混桶 = 报混合分布。
3. **hilog 会滚掉**。16 MB 环形缓冲，实测一轮跑完约 40 分钟后 `LprCamera` 的行完全消失
   （本轮靠设备持久化文件 `/data/log/hilog/hilog.NNN.*.gz` 才恢复出 06:04 那轮）。
   **主证据必须是 App 自己落盘的 `filesDir/camera_run_<ts>.log`**，hilog 只作辅证。
4. **量性能前先跑 `tools/check_native_build_flags.py`**（不需要设备）。`-O0` 慢 4 倍且无报错。
5. **热档必须记录**。热档 2→3 时 NPU 延迟 +15~20%，跨轮比较只在同热档内做。
6. **观测不到时，先问「观测代码有没有被执行」**。5.1 的 callback 档就是
   「看着像回调停摆，实际是缓冲填满」；本轮还额外踩到「相机页没起来是因为权限弹窗」
   —— 两者症状都是「没有 STREAM START」，必须靠 dumpLayout 区分。
7. **【本轮新增，最贵的一条】「隔离基准」与「流水线内」不是同一个数**。
   同一模型、同一后端、同一线程数，隔离 7.4 ms vs 流水线 19.5 ms（2 倍）。
   **不要把论文里的隔离基准数字直接当成产品路径的成本**，反之亦然。
   凡是要下「某段占多少 ms」的结论，**必须说明是在哪种条件下测的**。
8. **【本轮新增】否定的结果同样要落盘**。C4（线程数）与 C4b（绑核）都是
   **负结果**（默认已最优 / 绑定更慢），但它们**省掉了未来重复试错**，
   且 C4b 的「更凉的热档反而更慢」顺带**削弱了热降频假设**。
   **负结果不写下来，下一轮就会再试一遍。**
9. **【本轮新增】跨热档的比较要显式标注不严谨**。`aff1`（热档 1–2）与
   sweep1/2（热档 3–4）不同档，所以「cpu_a1 更慢」这条**只由隔离实验严格支持**；
   而「热档不是主因」这条**恰因方向相反而成立**。同一组数字，两个结论的
   证据强度不同 —— 必须分开写，不要笼统地说「实测证明」。
10. **【本轮新增】「不显著」可能只是「剂量不够」**。代码里一条旧结论说
    「sleep 3 ms 只把 p50 从 7.54 推到 8.71 ms，所以负载节奏解释证据薄弱」，
    据此把该假设搁置了很久。改用 8/16/33 ms 重做，效应是 **7.4 → 30.7 ms**。
    **做否定判断前，先确认自己扫到了剂量-反应曲线的上升段。**
11. **【本轮新增】要区分「相关」与「因果」，就得设计能分开它们的对照**。
    `gapMs` 把 p50 推高 4 倍只是**相关**；真正定性靠两个对照：
    ① **忙等**（`spinMs`，时间相同但 CPU 不空闲）—— 排除「时间本身」；
    ② **线程数**（`t1` vs `t4`）—— 把「频率」与「线程池唤醒」拆开。
    **一个变量的效应，往往需要另一个变量当尺子才能读出来。**
12. **【本轮新增】给探针加参数时，默认值必须保持历史行为逐位不变**。
    `gapMs`/`polluteKB`/`spinMs` 默认全 0，且返回值里**回显**这三个值 ——
    于是「档真的生效了」是**自证**的（`min < gapMs` 也证明 sleep 在计时区外），
    不依赖调用方记得自己传了什么。
