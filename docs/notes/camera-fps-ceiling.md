# 帧率还能再提吗：三条路的实测结论

**日期**：2026-09-21
**问题**：生产档 ~28 fps，能否再高？
**结论**：**能，但要换档位** —— 把检测器也放到 NPU 上（全 NPU 档）即可打满
相机 30 fps。降分辨率与并行化两条路**都走不通**（已实测证伪）。

---

## 一、结论表

| 方案 | 实测 | 结论 |
|---|---|---|
| 生产档（det=CPU rec=NPU） | ~28 fps | 基线 |
| **全 NPU 档（det/rec 都走 NNRT）** | **30.00 fps（±0.3，0 丢帧）** | ✅ **采用** |
| 降分析分辨率 640×480 → 480×480 | ~27 fps | ❌ 证伪 |
| 请求 60 fps（任何分辨率） | ~27–29.8 fps | ❌ 证伪 |
| JS 取帧/异步并行化 | 最多省 7 ms/帧 → 35 fps 理论 | ❌ 收益小于换档 |

---

## 二、采用：全 NPU 档打到 30 fps（⚠️ 但读错，见第六节）

```
实时识别中 · 全 NPU
到达 fps 30.0   完成 fps 30.0   丢帧 0 / 2076 帧到达

det  ⚡LANDED=NNRT:NPU_ohos.boot.hardware.kirin8020_v2_0  (req=nnrt)  l2=1121.6569
rec  ⚡LANDED=NNRT:NPU_ohos.boot.hardware.kirin8020_v2_0  (req=nnrt)  l2=4.0489
```

连续 10 个窗口：29.27 / 29.67 / 29.81 / 29.87 / 29.93 / 29.93 / 29.97 /
30.06 / 30.12 / 30.20 —— **抖动 ±0.3，稳定性与"基准档"同量级**。

**为什么它能到 30**：瓶颈从「我们的计算」转移到「相机」。

| | 生产档 | 全 NPU 档 |
|---|---|---|
| `conv` p50 | 6.10 ms | 6.12 ms |
| `infer` p50 | **21.78 ms** | **18.06 ms** |
| native 合计 p50 | **28.59 ms** | **23.45 ms** |
| 理论上限 | 35.0 fps | **42.7 fps** |
| 实测 | ~28 fps | **30.0 fps** |
| 相机帧预算占用 | 28.6 / 33.3 ms（86%） | 23.4 / 33.3 ms（70%，**富余 9.9 ms**） |

⚠️ **「理论上限 35.0 / 42.7 fps」是错的口径，2026-09-21 更正。**
那两个数是 `1000 / p50(frameMs)`，即**服务时间的倒数**，不是 fps。
`CONTEXT.md` 明确区分「服务时间 / 到达率 / 完成率」三个量，**只有后两者可以对外称 fps**。
本表里的 `infer p50` 还是**混桶**读数（检出帧与未检出帧混在一个滑动窗口里取中位数），
两种分布合成一个中位数，两者都不能直接换算成帧率。正确的读法是**余量**：
`33.3 ms − p50(frameMs)`。详见 `camera-npu-headroom.md`。

生产档的 native 28.6 ms 几乎吃满 33.3 ms 的帧预算，加上 JS 取帧/异步的
约 7 ms 就掉到 28 fps。全 NPU 档把 native 压到 23.4 ms，留出近 10 ms 余量，
于是稳定贴住相机的 30 fps。

## 三、证伪：降分辨率换帧率

试过把分析路 640×480 降到 480×480 并请求 60 fps：

```
STREAM START show=960x960 analyze=480x480 rot=90
FPS SET analyze requested=60-60 active=60-60
实测 ~27 fps
```

而 640×480 设 30-30 实测 28–30 fps —— **降分辨率后反而略低**。

汇总三次实测，说明 **~30 fps 是传感器/ISP 的上限，与分辨率无关**：

| 分辨率 | 请求 | 实测 |
|---|---|---|
| 640×480 | 30-30 | 28–30 fps |
| 640×480 | 60-60 | ~29.8 fps（active 报 60-60，实际只给 30） |
| 480×480 | 60-60 | ~27 fps |

既然换不到帧率，就该保持 640×480 以保住小车牌检出率。
`ANALYZE_TARGET_W` 已回退为 640 并在注释写明结论，避免下一轮再试。

**注意 `active=60-60` 是个陷阱**：API 接受请求并回报成功，但传感器并不兑现。
**必须实测到达率，不能信协商结果** —— 这与 `-O0` 那次同属"接口说 OK 但事实相反"。

---

## 四、证伪：并行化（收益太小）

生产档每帧预算拆解：

```
相机给 30 fps   -> 帧预算 33.3 ms
实测 ~28 fps    -> 每帧 35.7 ms
  native        -> 28.6 ms
  JS取帧+异步   ->  7.1 ms   <- 并行化只能省这一块
```

即便把这 7.1 ms 全部消掉，理论上限也只从 35.0 提到"贴住 30"——
而**换档位已经直接拿到了这个结果**。为 7 ms 去改并发结构，
收益/风险比远差于切到全 NPU 档。故不做。

---

## 五、给论文的一句话

**在这台设备上，30 fps 是相机侧的硬上限**（与分辨率无关，请求 60 不被兑现）；
**能否达到它，取决于检测器放在哪里**：

- 检测器在 CPU：native 28.6 ms/帧，吃满预算，只能到 ~28 fps
- 检测器在 NPU：native 23.4 ms/帧，留 9.9 ms 余量，稳定 30 fps

即：**把 NPU 用好不是"更快一点"的问题，而是"能不能达到传感器上限"的分界**。
这比单纯的加速比更能说明"落点"为什么重要 —— 同一条流水线，
只改一个角色的落点，就从"跟不上相机"变成"贴住相机"。

引用时必须标注：全 NPU 档下 det 的 `l2` 为 1121.6569（生产档为 1076.7692 量级），
**两档的指纹不同**，说明确实换了计算路径，不是同一数据的重复测量。

## 六、⚠️ 全 NPU 档的 30 fps 是在「读错」的前提下达到的

**这条没查之前，我差点把「全 NPU 档 30 fps」当成干净的性能结论写进论文。**

同一批数据的 E2E 矩阵（开机自检，`evidence/e2e_matrix_det_backend.log`）显示：
当**检测器**走 NNRT 时，参考图会被读错。

| det 的 req | LANDED | 结果 | match |
|---|---|---|---|
| `cpu` | CPU | `苏ED5172` | **1** |
| `gpu` | CPU（回落） | `苏ED5172` | **1** |
| `kirin` | CPU（回落） | `苏ED5172` | **1** |
| `nnrt` | NNRT:NPU… | **`苏E05172`** | **0** |
| `nnrt_fp32` | NNRT:NPU… | **`苏E05172`** | **0** |
| `nnrt_fp16` | NNRT:NPU… | **`苏E05172`** | **0** |

三个 NNRT 变体**全部**读错，且错法一致 —— 在省位后**插入一个 `0`**，
于是长度变成 **8 字符（非法，合法为 7/8 但结构不对）**。
每个 (role, backend, LANDED) 组合重复多次都是同样结果，
**这是该落点下的确定性行为，不是偶发抖动**。

日志原文（`evidence/e2e_matrix_det_backend.log`）：

```
E2EMATRIX RESULT role=det backend=cpu        LANDED=CPU        match=1 code=苏ED5172
E2EMATRIX RESULT role=det backend=nnrt       LANDED=NNRT:NPU…  match=0 code=苏E05172
E2EMATRIX RESULT role=det backend=nnrt_fp32  LANDED=NNRT:NPU…  match=0 code=苏E05172
E2EMATRIX RESULT role=det backend=nnrt_fp16  LANDED=NNRT:NPU…  match=0 code=苏E05172
```

即：**det 在 CPU 时 match=1，det 在 NNRT 时 match=0**。

而相机页的「全 NPU」档**正是 det 走 NNRT** ——
所以：**30 fps 是在识别错误的前提下达到的。**

### 为什么前面几节没发现

我只测了帧率和落点（`LANDED=` 显示 det 确实在 NPU 上，于是以为一切正常），
**没有同步核对识别结果**。落点自证只能证明"跑在哪个后端上"，
**不能证明"算对了"** —— 这正是 ADR-0003 里"指纹是报警器不是判据"的
另一面：**落点正确 ≠ 结果正确**，两者都要看。

### 因此「全 NPU 档 30 fps」不能单独引用

正确的表述必须是：

> 全 NPU 档（det/rec 均走 NNRT）可让流水线富余 9.9 ms/帧、达到相机 30 fps 上限；
> 但**同一落点下参考图被读成 `苏E05172`（8 字符、非法），识别错误**。
> 即 30 fps 与正确识别**不可兼得**（在本设备的当前模型与转换配置下）。

### 待办（引用前必须补）

1. 确认这是**检测器**的问题还是**转换配置**的问题 ——
   三个 NNRT 变体错法一致，倾向于检测模型在 NNRT 上的数值行为差异，
   而非 fp16/fp32 精度问题（因为 fp32 也错）。
2. 在**多张图**上统计全 NPU 档的准确率，不能只用参考图一张。
3. 若确认是转换问题，尝试重新转换 det 模型后复测；
   若确认是 NNRT 的确定性数值差异，则该档位**只能用于性能上限测量**，
   不能用于识别结果。

**在此之前，论文中若出现 30 fps，必须同时出现上述错误结果。**


**根因已查清（详见 `det-backend-alters-result.md`）：不是转换/配置 bug。**

box 的取整坐标两次完全相同（`1751|747|1879|855`），但

- `detConf`：0.7273 (CPU) vs 0.7230 (NPU) —— 亚像素坐标不同
- `cropSum`：**2773473 (CPU) vs 2763123 (NPU)** —— 送进识别器的像素不同

亚像素差异经**透视矫正**放大，把 `D` 读成 `0`。
**fp32 也错**，所以不是精度问题 —— 重新转换模型大概率修不好。

## 七、⚠️ 2026-09-21 补：30 fps 那批数据**全程未检出**，且含相机爬坡期

本节 §二 引用的「全 NPU 档 30.00 fps（±0.3，0 丢帧）」有两个**当时没查**的前提问题。
两个都是复查 06:04 那轮真机数据时发现的（原始 hilog 已从设备持久化文件
`/data/log/hilog/hilog.477/478.*.gz` 恢复 —— 16 MB 环形缓冲里它已经滚掉了）。

### 7.1 全程 `count=0`：那 30 fps 是**空帧**跑出来的

恢复出的 15 条 `STAGE` 行**全部 `count=0`**，4 个 `RATE` 窗口
（`arrive=29.69–30.82 / done=29.99–30.32 / dropped=0`）也全部 `hit_n=0`。

未检出帧不跑透视矫正 / 识别 / 判色，比检出帧便宜一大截。所以「全 NPU 档贴住
相机 30 fps」这句话，在**有车牌**的场景下**从未被测过** —— 它与 §六 的准确率警告
叠加：那一档既读错参考图，又只被证明过空帧吞吐。

### 7.2 含相机爬坡期：开流后 ~30 s 只有 1.4–5 fps

同一批数据里，开流后 13 个窗口的到达率是
`14.19 → 4.91 → 3.46 → 5.38 → 2.90 → 1.44 → 1.99 → 3.40 → 2.01 → 1.68 → 2.43 → 9.37 → 28.41`。
即**先崩到谷底再爬回 30**。当时的 `WARMUP_FRAMES = 10`（≈0.33 s @30fps）**完全没覆盖**。

根因在相机侧，不在我们这侧：相机 daemon 在开流后 0.4 s 报
`setMaxFps mCurMaxFps=0 -> 27`，切档后才 `27 -> 30`
（`CameraDaemon/IPS_STREAMIMG: Misc.cpp:4026`）。

### 7.3 因此本节所有帧率数字的引用方式

- 「30.00 fps」**只能**作为「相机侧上限 ~30 fps」的旁证（基准档也独立支持这条），
  **不能**作为「全 NPU 档能跟上相机」的证据。
- 需要「全 NPU 档在有车牌时的吞吐」时，必须用分桶 + 稳态门重采的数据
  （见 `camera-npu-headroom.md`）。
- 相机爬坡期必须被排除，否则任何「稳态」数字都掺着 1.4 fps 的窗口。
