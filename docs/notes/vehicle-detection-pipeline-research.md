# Research · 车辆识别流水线（车辆检测 → ROI → 车牌检测 → 识别 + 颜色）

- **日期**：2026-09-22
- **状态**：调研完成；**ROI 前置在 CCPD 分布上已实测证否**（第五节，n=1000 + 6 档尺度扫描）；
  架构**已定案**为「并行双路 + ROI 兜底」（第六节）。
  ⚠️ **真实监控场景未被本数据集覆盖** —— 见 5.7 的外部效度边界。
- **前置**：ADR-0005（颜色用像素测量）、ADR-0007（RQ 收口）、ADR-0008/0009（App 与装机）
- **证据**：`lpr-kirin8020-app/_veh/*.json`（6 份，全部可复跑）

## 三、模型选型：YOLOv5，**不能选 YOLOv8**

### 反面证据（本机实测记录，`D:\Tools\mindspore-lite\yolo_conv.txt` / `yolo_conv2.txt`）

```
InferShapeByNNACL for op: /model.22/dfl/conv/Conv failed
InferSubgraph index: 0 failed, ret: -500
Convert model failed, ret=Common error code.
```

`model.22/dfl` 是 **YOLOv8 的 DFL（Distribution Focal Loss）** 模块。
两份日志（两次独立尝试）均因此失败，**产物为零**。⇒ **选 YOLOv8 等于重走这条已证否的路。**

### 正面证据

1. **架构与现有管线一致**：`y5fu_320x_head` 本身就是 YOLOv5（`ncnn.param` 里是
   `Convolution + Swish(silu) + ConvolutionDepthWise` 的典型 v5 骨架）。
2. **NPU 落点已验证**（nova 14 Pro 实测）：含 decode（rank-5 常量 ×12）回落 CPU；
   **裁掉 decode 到 rank-4 → NPU，4.95 ms**（CPU 9.07）。
3. **COCO 预训练天生含车辆类**：car / bus / truck / motorcycle。

### ⚠️ 选型执行中的两个真实坑（本轮踩到）

1. **ultralytics 8.4 会把 `yolov5s.pt` 换成 `yolov5su.pt`**（v5-u，anchor-free + DFL）。
   导出的 ONNX 立刻被 `tools/scan_onnx.py` 抓到
   `/model.24/dfl/Transpose perm=[0, 3, 1, 2] NOT SUPPORTED` ——
   **正是 YOLOv8 失败的同一根源，不可用于 NPU 转换**。
   ONNX 静态扫描（几秒）先于转换（几分钟）拦下了它。
2. **ultralytics 的 `model.export()` 自己决定落盘文件名，忽略外部传入的 `--out`** ——
   先导 320 再导 640，第二次**静默覆盖**了第一次的产物（两条命令都"成功"）。
   已在 `_veh/export_yolov5.py` 里改成导出后 `os.replace` 到目标名，并加了存在性提示。

## 四、原始设计（含未经验证的关键假设）

```
整车图 720×1160
   ├─[1] 车辆检测（YOLOv5s COCO，取 car/bus/truck/motorcycle）
   ├─[2] ROI 截取（每辆车 bbox 外扩一点，裁出子图）
   ├─[3] 车牌检测（现有 y5fu_320x_head，**对每个 ROI 各跑一次**）
   ├─[4] 透视矫正 → 裁切
   └─[5] 车牌识别（rpv3/lprnet）+ 颜色（像素测量，ADR-0005 口径）
```

**[2] 的前提假设**：「车牌检测从整图 320×320 变成 ROI 320×320，等效于放大了车牌的分辨率，
可能改善小牌 / 远牌 / 多车场景的召回」。这条假设从未被验证过，本轮就是来测它的。

## 五、实测：ROI 前置**不成立**（n=1000 + 6 档尺度扫描）

### 5.1 前提事实（`probe_roi.json`）

| 量 | 值 |
|---|---|
| 图幅 | 720×1160 |
| 车牌中位尺寸 | **253×95 px**，占图 **2.92%** |
| letterbox 到 320 后车牌 | **70×26 px** |
| 通用车辆检测器（YOLOv5su/COCO）整车检出率 | **86.7%**（320 输入）/ 45.0%（640 输入） |

**第一个反直觉事实**：CCPD 上 letterbox 后的车牌有 **70×26 px** ——
**这不是小目标**，已在车牌检测器的舒适尺度内。

### 5.2 我的后处理自证（`diag_scale.json`）

ROI 实验依赖自实现的 letterbox + NMS，先证明它无偏（同一张图、同一阈值）：

| 路径 | 有车图比例 | 框总数 |
|---|---|---|
| ultralytics 原生 320 | 91.7% | 34 |
| **自实现 320** | **87.5%** | 30 |
| ultralytics 原生 640 | 58.3% | 22 |
| **自实现 640** | **54.2%** | 21 |

自实现与原生推理在同一输入下差异 ≤5%（letterbox 取整 / NMS 实现差），**后处理可信**。

**同时暴露第二个反直觉事实**：**640 反而比 320 差得多**（58% vs 92%）。
CCPD 是停车场近景、整车占画幅很大，640 下车辆被放大到偏离训练分布；320 反而把车缩回正常尺度。
⇒ **车辆检测必须用 320，不能用「常识上更准的 640」。**

### 5.3 主对比（`roi_vs_direct_full.json`，n=1000，判据 IoU≥0.5）

| 车辆输入 / ROI 外扩 | 直检召回 | ROI 召回 | Δ | 无车辆图 | 耗时 |
|---|---|---|---|---|---|
| **320 / 0.15** | **100.00%** | 85.10% | **−14.90%** | 13.4% | 20.9 → 107.2 ms |
| 320 / 0.40 | 100.00% | 85.50% | −14.50% | 13.4% | 20.9 → 104.0 ms |
| 640 / 0.15 | 100.00% | 32.40% | −67.60% | 57.0% | 20.9 → 123.8 ms |
| 640 / 0.40 | 100.00% | 33.20% | −66.80% | 57.0% | 20.9 → 122.3 ms |

- **直检召回 100.00%** —— 天花板已顶满，ROI **没有任何提升空间**。
- 加大外扩（0.15→0.40）几乎不改变结果 ⇒ 失败不是"ROI 裁太紧"。
- ROI 路还慢 **5.1 倍**。

### 5.4 失效归因（`why_roi_fails_n200_320.json` + `roi_zoom.json`）

> 同目录的 `why_roi_fails_n200.json` 是**首版用 640 车辆输入**跑的，检出率被 640 的缺陷
> 压低（见 5.2），**数值不可用**，只作为「发现尺度陷阱」的过程留档。

| 问题 | 实测 | 结论 |
|---|---|---|
| 车辆框圈住车牌了吗？ | 车牌被车框覆盖 **中位 1.000**；中心在内 **97.6%**（164/168） | ✅ 圈住了 |
| 那为什么不行？ | 两框 **IoU 仅 0.051** → 车辆框面积 ≈ 车牌框的 **19.6 倍** | 框太大 |
| ROI 放大了多少？ | **1.624×**（ROI 占整图面积中位 **52%**） | 确实放大了 |
| 放大有用吗？ | 召回反而 −14.9% | ❌ 无边际收益 |

**机制**：直检时车牌已有 70×26 px，**在检测器舒适区**；
ROI 的 1.6× 放大不产生任何边际收益，而它引入的"必须先检出车"这一**串行依赖**
带来 13.4% 的净损失。

### 5.5 尺度扫描：ROI 有没有适用区间？（`scale_sweep_inset_n200.json`）

> ⚠️ 首轮扫描（`scale_sweep_n200.json`）**设计有缺陷**：直接缩小整图，被 letterbox 补偿掉了
> —— 5 档的"牌宽@输入"**全是 71.8px**，自变量根本没动。
> 正确做法是**保留画布、把内容缩小后居中嵌入**（`--mode inset`），下表是修正后的结果。

| scale | 牌宽@输入 | 直检召回 | ROI 召回 | Δ | 无车辆率 |
|---|---|---|---|---|---|
| 1.0 | 71.8 px | 1.0000 | 0.8250 | −0.1750 | 0.160 |
| 0.5 | 35.9 px | 1.0000 | 0.8500 | −0.1500 | 0.145 |
| 0.35 | 25.1 px | 0.9950 | 0.8450 | −0.1500 | 0.155 |
| 0.25 | 17.9 px | 0.9950 | 0.7850 | −0.2100 | 0.215 |
| 0.18 | 12.9 px | 0.9300 | 0.5600 | −0.3700 | 0.440 |
| 0.12 | 8.6 px | 0.5500 | 0.0550 | −0.4950 | 0.945 |
| **交叉点** | | | | **不存在** | |

**从 71.8px 到 8.6px 的整个范围内，直检始终优于 ROI，没有交叉点。**
且车牌越小、ROI 崩得越快 —— 因为**车辆检测器比车牌检测器更脆弱**：
车牌 8.6px 时无车辆率已达 **94.5%**，ROI 路先归零。

### 5.6 核心洞察（可推广）

> **串行流水线的召回 = 各环节召回的乘积。**
> 把召回 85% 的环节（通用车辆检测）放到召回 100% 的环节（专用车牌检测）**前面**，
> 总召回必然 ≤85%。
>
> 「先框车再找牌」只在**车辆检测器不弱于车牌检测器**时才可能成立。
> 用通用 COCO 模型做前置，它必然成为瓶颈。

### 5.7 补测误检维度 & 外部效度边界（用户 2026-09-22 指出）

用户指出：真实用法是「**摄像头实时**，干扰多，**得放大来看**」。
这打在两个缺口上 —— 一个是我的漏测，一个是本数据集的结构性限制。

#### 缺口一：本轮只测了召回，从没测误检 → 已用现有数据补算（`fp_analysis.py`）

| 配置 | 召回 | 框/图 | 零检率 | 多框率 | 冗余框/命中 | 干净命中率 |
|---|---|---|---|---|---|---|
| **直检** | 1.0000 | **1.005** | 0.0000 | **0.0050** | **0.005** | **0.9950** |
| ROI 320 / 0.15 | 0.8510 | 0.870 | 0.1450 | 0.0150 | 0.022 | 0.8360 |
| ROI 320 / 0.40 | 0.8560 | 0.864 | 0.1430 | 0.0070 | 0.009 | 0.8490 |

**直检每张图几乎正好输出 1 个框**（1005 框 / 1000 图），多框率仅 0.5%。
即：CCPD 上**不存在"干扰导致的误检"可供减少**，ROI 反而把多框率抬到 1.5%。

#### 缺口二（本数据集无法补）：**CCPD 是天花板数据集**

直检在 CCPD 上同时达到「召回 100% + 单框率 99.5% + 平均 IoU 0.85」——
**它对直检已经没有任何改进空间**。因此 CCPD
**既不能证实、也不能证伪** ROI 在困难场景下的价值。

⇒ **「CCPD 上 ROI 无收益」≠「真实场景 ROI 无收益」。**

本轮结论的**严格适用范围**应表述为：

> 在「车牌已足够大、单目标、背景干净、直检接近天花板」的分布上，
> 「车辆检测 → ROI → 车牌检测」作为**前置**是净亏损。
> 真实监控场景（远距离、多目标、强干扰、车牌倾斜）**尚未被本数据集覆盖**。

#### 这正是架构选「兜底(OR)」而不是「删掉 ROI」的原因

| | 前置 AND | 兜底 OR |
|---|---|---|
| CCPD（本轮实测分布） | −14.9% 召回 | **不触发 → 零成本、零损失** |
| 真实困难场景（未覆盖） | 未知 | **自动生效，可能带来放大收益** |
| 对「结论能否外推」的不确定性 | 脆弱 | **免疫** |

兜底设计的价值不在当下，而在**它把这个未解的不确定性变成了不影响主路径的储备**。

#### 要真正验证用户的场景，需要什么

1. **真实监控/卡口素材**（远距离、多车、强干扰）—— 公开数据集（如 UA-DETRAC、
   或带整车的道路监控集）或用户自有摄像头素材；
2. 在那份素材上重跑 `_veh/roi_vs_direct.py`（脚本与判据均可直接复用）；
3. 重点看**误检率**与**低置信场景的 IoU**，而不只是召回 —— 那才是 ROI 最可能赢的地方。

### 5.8 ROI 路已优化到上限再对比（用户坚持 ROI 前置后追加）

用户澄清「得放大来看」= 截 ROI 检测识别，即**坚持原始设计**。
既然要做，就先把它调到最好再比 —— 结果 ROI 确实能大幅改善，但仍追不平：

| 车辆置信阈值 | 取几个车框 | ROI 召回 | Δ | 车框/图 | 用ROI/图 | 耗时 |
|---|---|---|---|---|---|---|
| 0.25 | top1 | 0.8250 | −17.5% | 1.14 | 0.84 | 42.9 ms |
| 0.05 | top1 | 0.8950 | −10.5% | 1.77 | 0.93 | 46.4 ms |
| 0.10 | **全部** | 0.9000 | −10.0% | 1.47 | 1.47 | 53.5 ms |
| **0.05** | **全部** | **0.9100** | **−9.0%** | 1.77 | 1.77 | 55.6 ms |

**两条优化都是实质性的（82.5% → 91.0%，+8.5 个百分点），必须写进实现：**

1. **车辆检测必须用极低置信阈值（0.05，而非默认 0.25）。**
   在 ROI 前置里，车辆检测器的评价标准**不是 mAP 而是召回** ——
   多框的代价只是多跑几次车牌检测，漏检的代价是**召回归零**。
   ⇒ 「宁误检不漏检」。实测把无车辆率从 16.0% 砍到 7.5%。
2. **必须遍历所有车辆框**，不能只取最高分那个。
   一帧多车时车牌可能落在非最高分的车框里。实测再补 1.5 个百分点。

**但仍差 9.0%**，且剩余差距几乎全部（7.5 / 9.0）来自「**车辆完全检不出**」，
不是 ROI 内部的问题 —— 阈值再降到 0.01 也无法继续改善（无车辆率下限 ≈6%）。

#### 收益条件（这才是判断 ROI 是否划算的公式）

```
ROI 前置划算  ⟺  P(直检失败 且 车辆成功)  >  P(车辆失败) + 不可比的精度损失
```

CCPD 上 **P(直检失败) = 0**（直检召回 100%），所以左边恒为 0、ROI 必输。
真实场景里左边不为 0，**结论有可能翻转** —— 但这必须用真实素材测，本数据集无法回答。

## 六、定案：并行双路 + ROI 降级为「兜底」（用户 2026-09-22 拍板）

**决策**：不采用「车辆检测 → ROI → 车牌检测」的串行前置；
改为**并行双路**，并把 ROI 从**前置（AND）**降级为**兜底（OR）**。

### 6.1 为什么「前置 → 兜底」在数学上就已经赢了

```
前置(AND):  召回 = R_车辆 × R_车牌|ROI          ≤ R_车辆       ← 实测 85.1%
兜底(OR):   召回 = R_直检 ∪ (R_车辆 × R_车牌|ROI) ≥ R_直检     ← 实测下限 100%
```

OR 关系意味着**兜底路径在最坏情况下也只是不生效，不可能降低召回**；
而 AND 关系把前置环节的召回直接变成了总量上限。

### 6.2 架构

```
整车图 720×1160
   ├─[主路] 车牌检测（全图 y5fu_320x）              20.9 ms
   │     ├─ 检出 → 矫正 → 裁切 → 识别 + 颜色（ADR-0005 像素测量）
   │     └─ 未检出 → 触发兜底 ↓
   └─[辅路] 车辆检测（全图 YOLOv5s，320）            与主路并行
         ├─ 车辆框 → 可视化层 + 车牌归属（多车场景）
         └─ 兜底路径**直接复用**这些框（零额外成本）
              └─ 对每个车框裁 ROI → 车牌检测 → 框映射回原图 → 并入结果
```

### 6.3 三个关键点

1. **兜底的车辆检测是免费的** —— 辅路为了可视化本来就要跑车辆检测，兜底复用它，
   不产生第二次推理。
2. **只在失败时付费** —— CCPD 上直检召回 100% → 兜底几乎不触发 → 召回与延迟
   都与「纯直检」相同；真实远距离素材上直检会失败，那时才付出 ROI 的代价。
3. **触发判据不用硬编码阈值** —— 判据是「本次全图检测是否产出有效车牌」，
   一个运行时直接可观察的事实，而不是拍脑袋的 px 阈值。

### 6.4 与「给一个手动开关」的区别

用户的选项是「并行双路 + 保留 ROI 可选开关」。实现上**不做一个手动开关**，理由是：
手动开关的默认值要么是关（等于没做），要么必须由人判断何时开（把判断成本推给人）。
**自动兜底**把同一个诉求实现成「不需要开关的开关」——条件满足时它自己生效，
而本轮已用数据证明该条件在 CCPD 上永不为真，所以它没有副作用。

### 6.5 诚实边界

本轮**没有**证明兜底能提升召回 —— 在 CCPD 上它永不触发。
它的价值是**面向未来素材的鲁棒性储备**，不是当下的性能收益。
文档与演示页都必须这样表述，不得包装成「提升了召回」。

### 6.6 ROI 路径的实现必须包含两条实测优化

用户明确「得放大来看」= **截 ROI 检测识别**（不是交互式放大）。
既然这条路径要做，就必须按 5.8 的实测结果实现，否则会平白丢掉 **8.5 个百分点**的召回：

1. **车辆检测用极低置信阈值**（起点 0.05，可配）——
   ROI 前置里车辆检测器的目标是**召回**而非 mAP，「宁误检不漏检」。
2. **遍历所有车辆框**，逐框跑车牌检测并把结果并回原图坐标 ——
   不得只取最高分车框（一帧多车时这是错的实现）。

两条合起来把 ROI 路从 82.5% 提到 **91.0%**。

## 七、风险与边界（必须如实交代）

1. **车辆检测精度无 GT，不可声称 mAP。** CCPD 每张图只标了**一个**车牌框，
   没有车辆框标注。产出只能是「可视化 + 未做定量评估」。
2. **多车归属无法在 CCPD 上验证。** 单车标注 → 无法验证「A 车配 A 牌」。
   若要在作品集里展示这个价值点，需要**另找多车场景图**。
3. **许可问题**：ultralytics YOLOv5 是 **AGPL-3.0**。
   用于推理通常不构成衍生作品，但**权重文件入库需标注许可**，
   公开作品集仓库应说明来源（`scan_for_publication.py` 会扫这类资产）。
   备选 YOLOX（Apache-2.0）架构不同、**无法复用现有 YOLOv5 管线**，权衡后仍建议 YOLOv5 + 写明许可。
4. **本轮结论的适用范围**：证否的是「**用现成通用检测器做前置**」这条路，
   不是"ROI 在原理上永远无用"。若将来有一个**在 CCPD 尺度上训练过、召回接近车牌检测器的**
   车辆检测器，结论需要重测（`_veh/roi_vs_direct.py` 可直接复跑）。
