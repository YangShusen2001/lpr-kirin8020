## 一句话结论

**同一份 1000 张真实图、同一个探针，只改变一个角色的落点：
换 rec 只让 3 张输出不同（0.3%），换 det 让 68 张不同（6.8%）—— 差 22.7 倍。
「检测器才是敏感环节」从此有 n=1000 对 n=1000 的同输入证据。**

---

## 一、为什么做

`det-backend-alters-result.md` 证明了「det 落点会改变识别输出」，但那是 **n=1**
（只有参考图一张），笔记自己把「多图统计」列为待办 1。
且当时无法判断：这究竟是**检测器特有的现象**，还是**任何角色换后端都会有的
普遍现象**？本轮把两个角色都测了，用的是**同一份数据、同一个探针**，
唯一差别是变哪个角色 —— 因此两者**可直接对比**。

## 二、实验设计

- **唯一变量是被测角色的落点**：该角色载入两份会话（`cpu` / `nnrt`），
  其余两个角色固定生产配置。每张图跑两遍 pipeline，只换那一个会话 id。
- **落点已自证不同**（`CROPAB LOAD` 行，两次实验各自记录）：
  - det cpu → `backend=CPU;attemptLog=CPU(ok)`；det nnrt → `backend=NNRT:NPU_ohos.boot...v2_0`
  - rec cpu → `backend=CPU`；rec nnrt → `backend=NNRT:NPU_ohos.boot...v2_0`
  - 同一份模型文件、同 inputShape，无 fallback
- **真值 = 文件名**（`CONTEXT.md`）。两轮 `bad_gt` 均为 **0**
  —— 1000 张真值长度全是 7/8，没有 t6 那种「文件名被工具改过、凭空制造
  29 条长度错误」的污染。

## 三、结果（两轮可直接对比）

| 变哪个角色 | n | **agree** | 不一致 | ok_cpu | ok_np |
|---|---|---|---|---|---|
| **rec**（识别器） | 1000 | **997（99.7%）** | **3（0.3%）** | 608 | 609 |
| **det**（检测器） | 1000 | **932（93.2%）** | **68（6.8%）** | **609** | **581** |

**分歧率相差 22.7 倍。** 且方向一致地对 NPU 不利：det 换 NPU 后准确率
609 → 581（−28 张），而 rec 换 NPU 是 608 → 609（+1 张，噪声内）。

### det 分歧的 68 张里，对错怎么变

| 类型 | 张数 | 含义 |
|---|---|---|
| **仅 CPU 对** | **33** | 落点确实改变了结果，且 CPU 版是对的 |
| 仅 NPU 对 | 5 | 落点改变了结果，NPU 版是对的 |
| 两端都错 | 30 | 落点只改变了**错法** |

**38 张伴随长度变化**（如 `皖A0C911 → 皖A0C91`、`皖A28S79 → 皖A28S7`，末位被切），
30 张等长替换。

### 错误位置高度集中（与 `det-backend-alters-result.md` 的机理互证）

det 分歧的样例，**绝大多数错在首位（省份）**：

```
川JK0707  cpu=粤JK0707   np=1JK0707     <- 首位换字 / 丢字
浙C510W8  cpu=苏510W8    np=510W8       <- 首位换字 / 丢字
皖A15C18  cpu=皖A15C18   np=京A15C18    <- 仅 NPU 错，首位
皖A15X05  cpu=皖A15X05   np=苏A15X05    <- 仅 NPU 错，首位
```

这正是 `det-backend-alters-result.md` 描述的机理：**检测器亚像素坐标差异 →
透视矫正放大 → 首字符翻转**。本轮把那个 n=1 的观察扩成了 68 例，
且**错误位置与机理预测一致**（集中在被矫正放大的省份位）。

### 错误位置量化：集中在被矫正的**两端**

68 张分歧里（可重叠计数）：

| 位置 | 张数 | 占比 |
|---|---|---|
| **首位（省份）** | **43** | 63% |
| **末位** | **27** | 40% |
| 中间（位 1–5） | **2** | **3%** |

**中间 5 个字符里只有 2 张出错。** 这与机理完全吻合：透视矫正按 det 给出的
四边形重采样，**边缘像素**的插值误差最大，而 plate 串的两端恰好落在边缘。
也就是说，det 落点差异不是「随机污染整个串」，而是**系统性地攻击被矫正图像的两端**。

## 四、诚实的边界（引用前必读）

1. **绝对准确率不是识别器的准确率，不可与 t6 的 90.6% 比。**
   本探针把 94x24 的**裁剪小图**喂进**完整流水线**（det 要在这张小图上重新找牌
   → 透视矫正 → rec），而 t6/A16 是**直接把裁剪图喂给识别器**（bare head）。
   证据：rec 那一轮的长度错误率 **25.8%（258/1000）**，而 A16 实测 rpv3 的
   长度错误率只有 **1.0%（10/1000）** —— 差 25 倍，说明输入被这条配置劣化了，
   不是识别器退步。**A/B 结论不受影响**（两端共享同一条劣化路径）。
2. **det 那一轮的输入是裁剪图而非整车图**，det 的工况与真实场景不同
   （真实场景里 det 面对的是整幅画面，这里面对的是一张已经是车牌的小图）。
   所以 6.8% 这个数**只能与同输入的 rec 0.3% 并列**，
   **不能**外推成「真实场景下换 det 后端有 6.8% 概率读错」。
3. **两端准确率都不高（60.8% / 58.1%）**，原因同第 1 条。轮内对比有效，
   绝对值无效。

## 五、结论

> **换后端要不要重新验证输出？要。但该盯的是检测器，不是识别器。**
> 同一份数据、同一探针下，det 落点的分歧率是 rec 的 **22.7 倍**，
> 且 det 换 NPU 还净掉 28 张准确率。这给「端侧能否直接替换后端」
> （ADR-0003 的方法学主张）提供了一个**分层**的答案：
> **识别器可以按性能挑后端，检测器必须逐例验证输出。**

## 六、工程记录

- **数据集投递**：`hdc shell` 与 `hdc file send` 对 App 私有目录均
  permission denied（都是 shell uid）。最终把 1000 张（2.52 MB）打进 rawfile
  （`assets/crops`），HAP 92 → 94.9 MB。
- `resourceManager.getRawFileList` 与 `fileIo.listFile` 在本 API 版本
  **都返回 `Promise<string[]>`**，当同步数组用在编译期报
  「missing length/pop/push」。
- 探针按钮在「探针控制台」**页签**里（不是滚动）；
  `uitest uiInput swipe` 的 velocity 下限是 **200**（传 150 静默无效）。
- 探针已参数化为 `cropBackendAB(role)`，加新角色只需加一个按钮。
