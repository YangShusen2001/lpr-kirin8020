## 一句话结论

**识别器落点（rec: CPU vs NPU）在 1000 张真实图上只让 3 张输出不同（0.3%）。**
与之对照，`det-backend-alters-result.md` 里**检测器**落点一换，参考图立刻读错
（`苏ED5172` → `苏E05172`，三个 NNRT 变体全错）。**但两者的样本量差 1000 倍，
目前还不能说「检测器比识别器敏感」** —— 见「诚实的边界」一节。

---

## 一、为什么做

`det-backend-alters-result.md` 证明了「det 落点会改变识别输出」，但那是 **n=1**
（只有参考图一张），笔记自己把「多图统计」列为待办 1。本探针把样本量提到
整个真实数据集，测**同一问题的识别器版本**。

## 二、实验设计

- **唯一变量是 rec 的落点**：det/cls 固定为生产配置，rec 载入两份会话
  （`cpu` / `nnrt`），每张图跑两次 pipeline，只换 recId。
- **落点已自证不同**（日志 `CROPAB LOAD` 行）：
  - `rec cpu` → `backend=CPU;requested=cpu;attemptLog=CPU(ok)`
  - `rec nnrt` → `backend=NNRT:NPU_ohos.boot.hardware.kirin8020_v2_0;requested=nnrt`
  - 同一份模型文件 `models/rpv3_mdict_160_r3.ms`，同 inputShape `[1,48,160,3]`
- **真值 = 文件名**（`CONTEXT.md`：只有 `_dataset/real/crops/` 的文件名是真值）。
  `bad_gt=0` —— 1000 张真值长度全是 7/8，没有 t6 那种「文件名被工具改过、
  凭空制造 29 条长度错误」的污染。

## 三、结果

| 项 | 值 |
|---|---|
| n | **1000** |
| **agree**（两后端输出逐字一致） | **997（99.7%）** |
| 不一致 | **3（0.3%）** |
| ok_cpu（rec=CPU 命中真值） | 608（60.8%） |
| ok_np（rec=NPU 命中真值） | 609（60.9%） |

### 三处不一致（全部原文）

```
皖AG8T60  gt=皖AG8T60  code_cpu=皖AG8T6   code_np=皖AG8T66   （两端都错：少/多一位）
皖AS065M  gt=皖AS065M  code_cpu=5S065M    code_np=S065M      （两端都错：丢首位）
皖ASZ180  gt=冀ASZ180  code_cpu=冀ASZ180  code_np=皖ASZ180   （NPU 对、CPU 错）
```

第三例是唯一「换落点改变了对错」的：**NPU 对而 CPU 错**（省份位 冀→皖）。
另两例两端都错，落点只改变了错法。

## 四、诚实的边界（引用前必读）

1. **绝对准确率 60.8% 不是识别器的准确率，不可与 t6 的 90.6% 比较。**
   本探针把 94x24 的**裁剪小图**喂进**完整流水线**（det 要在这张小图上重新找牌 →
   透视矫正 → rec），而 t6/A16 是**直接把裁剪图喂给识别器**（bare head）。
   证据：本配置的**长度错误率 25.8%（258/1000）**，而 A16 实测 rpv3 的长度错误率
   只有 **1.0%（10/1000）** —— 差 25 倍，说明输入被这条配置劣化了，
   不是识别器退步。**A/B 结论不受影响**（两端共享同一条劣化路径）。
2. **「检测器比识别器敏感」尚未成立。** det 的结论是 n=1，rec 是 n=1000，
   样本量差 1000 倍。det 完全可能也只有 ~0.3% 的分歧率，只是我们那一张恰好命中。
   **要把两者并列，必须用同样的 1000 张图测 det 落点** —— 而这需要**整车图**
   （`_dataset/real/crops` 全是裁剪图，喂不进检测器）。这是下一步的真实缺口。

## 五、错误形态学（与 t6 互相印证）

rec=CPU 一端的逐位错误（1000 张）：

| 位 | 0（省份） | 1 | 2 | 3 | 4 | 5 | 6（末位） | 7 |
|---|---|---|---|---|---|---|---|---|
| 错误数 | **99** | 1 | 4 | 3 | 2 | 2 | **36** | 0 |

- **省份位仍是替换错误的主战场**（99/134 个替换错误行），与 t6 的
  「数据集偏斜不改变总准确率，但决定错误发生在哪一位」一致。
- 本配置额外引入一个 **长度错误模式（258 张，25.8%）**，A16 记的 rpv3 只有 1.0%
  —— 再次指向第四节第 1 条：这条配置劣化了输入。

## 六、工程记录

- **数据集投递曾被打着**：先试 `hdc file send` 推到 App 私有 filesDir，
  `hdc shell` 与 `hdc file send` **都是 shell uid，实测均 permission denied**。
  最终把 1000 张（2.52 MB）打进 rawfile（`assets/crops`），HAP 92 → 94.9 MB。
  换来「零权限、随包装走、可复现」。
- `resourceManager.getRawFileList` 与 `fileIo.listFile` 在本 API 版本
  **都返回 `Promise<string[]>`**，直接当同步数组用会在编译期报
  「missing length/pop/push」。
- 探针按钮在「探针控制台」**页签**里（不是滚动），`uitest uiInput swipe`
  的 velocity 下限是 **200**（用 150 会静默无效）。

## 七、下一步
