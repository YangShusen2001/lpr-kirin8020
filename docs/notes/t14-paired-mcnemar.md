# T14 · 配对 McNemar：端侧移植不是「保真」的（推翻 T11 的自我标注）

- **日期**：2026-09-21
- **设备**：HUAWEI nova 14 Pro（MIA-AL00）· 麒麟 8020 · HarmonyOS 6.1.0.135 · API 24
- **证据**：`evidence/crop_bare.log`（端侧，T11 落盘）+ 主机侧现场重跑
- **工具**：`tools/mcnemar_device_vs_host.py`、`tools/mcnemar_triplet.py`

## 一句话结论

**T11 的「移植保真」被推翻。** 配对 McNemar 给出 **p = 0.0156**，
且配对是**严格单向**的（端侧在 0 张图上赢，主机在 7 张上赢）——
**端侧确实比主机低 0.7 pp，不是抽样波动。**

---

## 一、为什么做

T11 报「端侧 NPU 89.9% vs 主机 onnxruntime 90.6%，只差 0.7 pp —— 移植是保真的」，
并在同一篇笔记的「诚实的边界」里自己写了：

> 0.7 pp 在 1000 张上约 7 张的量级，**不能排除是抽样波动**。

**这个保留意见是对的，而它把结论否掉了。** 本轮就是把这条保留意见做掉。

### 关键：必须用配对检验

两次测量用的是**同一批 1000 张图**（`sirius-ai/LPRNet_Pytorch` test 集）。
同一张图在两侧都对或都错，是因为**这张图本来就难** —— 这个共同方差在
两个独立置信区间里会各自计入，把差异淹没。

配对 McNemar 只看**不对称格**（仅 A 对 / 仅 B 对），消掉共同方差，检出力高得多。
1000 张上 0.7 pp 的差异，用独立 CI 看不出来，用配对检验**一眼就看出来**。

## 二、结果

### 主对比

| 对比 | 准确率 | 差 | 配对（仅前者对 / 仅后者对） | p |
|---|---|---|---|---|
| **端侧 NPU vs 主机 rpv3** | 89.9% vs 90.6% | **−0.7 pp** | **0 / 7** | **0.0156** |
| 端侧 CPU vs 主机 rpv3 | 86.7% vs 90.6% | −3.9 pp | 0 / 39 | 0.0000 |
| 端侧 NPU vs 端侧 CPU | 89.9% vs 86.7% | +3.2 pp | 38 / 6 | 0.0000 |

### 为什么这个结果不可能是噪声

**配对表是严格嵌套的**：

```
主机 rpv3   ⊃  端侧 NPU   ⊃   端侧 CPU
```

- 端侧 NPU vs 主机：主机赢的 7 张里，端侧**一张都没赢回来**（0 : 7）；
- 端侧 CPU vs 主机：主机赢 39 张，CPU **一张都没赢回来**（0 : 39）。

若差异只是噪声，两个方向都该有若干张 —— **两次都是 0**。
`0 : 7` 的精确二项双尾概率是 **0.0156**；`0 : 39` 是 **< 1e-9**。

> **端侧实现是主机实现的严格子集（就这 1000 张而言）：
> 主机能对的端侧不一定对，端侧能对的主机一定对。**

## 三、差异来自哪一层？两个候选

`crop_bare.log` 的同一批图上同时有 `code_cpu`（MS Lite **CPU** 后端）与
`code_np`（MS Lite **NNRT→NPU** 后端），**两者共用同一套 C++ 预处理**
（`LprEncodePlateInto`）。所以：

| 对比 | 后端 | 预处理 | 含义 |
|---|---|---|---|
| **CPU vs NPU** | 不同 | **相同** | **纯后端差异** |
| NPU vs host | 不同 | **不同**（C++ 移植 vs Python 参考） | 后端 + 预处理 |
| CPU vs host | 不同 | 不同 | 后端 + 预处理 |

**CPU vs NPU 也显著（+3.2 pp，p<0.0001）**，说明：

> **后端本身就是准确率的一个变量** —— 同一份 C++ 预处理、同一份模型文件，
> 只换 MS Lite 的后端（CPU → NNRT/NPU），准确率差 3.2 pp。

这与 T10/T12/T13 的**落点分歧率**结论不矛盾：那几轮测的是「换后端会不会
改变输出」，答案是**很少**（≤0.1% 真实场景）；本轮测的是「改变的那些
是否系统性地对某一侧不利」，答案是**是，且一致对 CPU 不利**。

> **分歧率低 ≠ 无偏。** 0.1% 的分歧若方向一致，仍会在 1000 张上累积成
> 统计显著的准确率差。这是 T10-T13 那组结论**没有覆盖**的维度。

## 四、对 T11 结论的更正

T11 写的是：

> 端侧 NPU 89.9%，与主机 onnxruntime 的 90.6% 只差 0.7 个百分点
> —— **移植是保真的**。

**更正为**：

> 端侧 NPU 比主机低 **0.7 pp，统计显著（配对 McNemar p=0.0156，0:7）**。
> 幅度小（1000 张里 7 张），**工程上可接受**，但**不能说成「保真」**。
> 端侧实现是主机实现的严格子集：主机对的端侧不一定对，端侧对的主机一定对。
> 且端侧内部 CPU 比 NPU 又低 3.2 pp —— **后端本身是准确率变量**。

**「保真」这个词用错了。** 移植在**数值路径**上是忠实的（同 shape、
同 NHWC 编码、T10/T12/T13 证明输出极少分歧），但在**准确率**上有一个
小而**系统性**的落差。两件事都要说。

## 五、诚实的边界

1. **7 张的量级意味着「具体差多少」不稳**：p=0.0156 说明「有差异」可信，
   但 0.7 pp 这个点估计的置信区间很宽。不要引用「正好 0.7 pp」，
   引用「**约 0.7 pp，显著但幅度小**」。
2. **主机侧是现场重跑的**，不是 T11 当时那份产物（A16 日志只打印分歧，
   没有全量逐图预测）。重跑值与 A16 记录的 906/1000 **一致**，
   这是可核对的；但严格说这是两次运行，若 onnxruntime 非确定性则配对有噪声。
3. **预处理差异与后端差异没有完全解耦**：端侧只有「C++ 预处理 + MS Lite」，
   主机只有「Python 预处理 + onnxruntime」，**没有交叉组合**
   （C++ 预处理 + onnxruntime，或 Python 预处理 + MS Lite）可测。
   所以「差异属于哪一层」只做到**指出两个候选**，没有定位到单一层。
   CPU-vs-NPU 那组能排除预处理，证明**后端至少是一部分原因**；
   但预处理是否**也**贡献，本设计回答不了。
4. 数据集是 7 字符裁剪图（`sirius-ai/LPRNet_Pytorch` test 集），
   结论不自动适用于 8 字符绿牌或整车场景。

## 六、工程记录

- 新增 `tools/mcnemar_device_vs_host.py`（单对比）与 `tools/mcnemar_triplet.py`
  （三对比，把后端与预处理两层分开）。
- **主机侧现场重跑**而不是抄 A16 的日志：A16 的产物只打印**分歧**，
  没有全量 1000 条逐图预测，无法配对。重跑复用 lpr-showcase 自己的
  `hlpr_reference`（`H.sess` / `H.imread_u` / `H.recognize`），
  **不复制预处理** —— 复制就会有两套实现，正是本项目反复踩的坑。
- 真值口径与 A16 一致：`stem.split('-')[0].split('_')[0]`。
- 重跑值 906/1000 与 A16 记录**逐位一致**，说明主机侧可复现。
