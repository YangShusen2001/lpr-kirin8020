# T3 · 相机实时：任务派发器丢任务

- **日期**：2026-09-21
- **票**：#6
- **对应 ADR**：ADR-0003（落点自证）、ADR-0004（单后端 MS Lite）
- **数据**：`evidence/t3_camera_throughput.log`（在 app 仓库）

## 现象

相机页长期显示「档位加载失败」，**相机流从未启动**，因此 T3 的吞吐指标一直
是空的（「丢帧 0 / 0 帧到达」）。票面因此挂着 `ready-for-human`。

## 定位

补上诊断日志后拿到关键事实：`loadModelAsync` 三次调用**全部返回空串**
（`rawlen det=0 rec=0 cls=0`），而 native 侧**一条 `loadModel` 日志都没有**
—— 说明请求根本没走到模型加载器。

根因在 `InferenceRunner`（`napi_init.cpp`）：它用**单个任务槽**而不是队列。

```
Submit:  task_ = fn; has_ = true; notify; wait(!has_)
Loop:    取 task_; 执行; has_ = false; notify_all
```

两个并发 Submit 时：

1. 第二个覆盖 `task_`，而 `has_` 已经是 `true`
2. 第一个跑完把 `has_` 置 `false` 并 `notify_all`
3. **两个提交者都被唤醒**，但第二个的任务从未执行
4. 第二个的 `job->kv` 保持空串 → Promise 静默 resolve 成 `""`

**触发条件是跨页面并发提交**：相机页 `ensureSessions` 加载模型的同一时刻，
首页的自动探针仍在后台提交任务。同页面内的串行 `await` 不会碰撞，所以这个
缺陷在只用一个页面时永远不出现。

## 修法

`std::deque<std::shared_ptr<Item>>`，每个任务自带 `finished` 标志与**自己的**
condition_variable —— 唤醒只针对该任务，不存在「唤醒错人」。任务仍在锁外执行，
推理期间不挡入队。

## 队列修好之后，又暴露出三个缺陷

修完派发器，相机页确实跑起来了（见下方真机数据）。但**一切档就再次停摆** ——
于是又查出三个独立缺陷。它们的共同点是：**只在「切档」这条罕用路径上出现**。

### ① 切档期间不腾接收器缓冲 ⇒ 相机永久停止回调

切一次档要连装三个模型（「全 NPU」档实测 ~24 s），而接收器只有 **8 格**。
原实现在 `switching` 时和 `busy` 一样**不读不释放**（把帧留在缓冲里）——
那是给「一帧工作略超帧间隔」设计的策略，只能积一两帧。切档期间 ~3.4 fps 会在
几秒内把 8 格填满；缓冲一满，相机**不再回调 `imageArrival`**，此后没有任何
事件能唤醒帧循环：画面显示「实时识别中」，却一帧都不出。

**修法**：切档期间走新增的 `drainOne()` —— 读出最新一帧**立刻 release**。
这些帧本来就要丢（新档 mode/slot 与旧会话不匹配，算出来是错的），
既不浪费信息，又让缓冲始终有空位。

### ② 切档结束后没人重新起帧

切档期间走 `drainOne` 分支，那条路径**不置 `pending`**，所以
`finishFrame()` 的接手条件 `pending && !switching` 不成立，kick 落空。
新增 `resumeFrames()` 显式起一帧。

### ③ 加载失败时「档位」与「实际会话」不一致

`switchGear` 先把 `this.gear` 改成新档，失败时会话仍是上一档 —— 这个组合会
拿旧会话去跑新档语义（mode/slot 不匹配），**静默算出错的东西**。
现在回退 `gear = loadedGear`，让两者重新一致。

### ④ 「N 帧到达」永远显示 0

`totalArrived` 直接渲染在读数卡上（「丢帧 x / N 帧到达」），却是普通
`private` 成员 —— 不触发重绘，真机上一直显示切档时清零的那个 0。
改成 `@State`。同文件其余 UI 绑定字段都已是 `@State`，**只有它漏了**。

## 真机验证

生产档（切档前）：

```
STREAM START show=960x960 analyze=640x480 rot=90
FIRST FRAME kind=NV21 decode=2 infer=103 rot=90
FRAME n=60  fps=3.65  plate=赣AD38888 split=6|1
RATE arrive=3.39 fps done=3.39 fps dropped_in_win=0 cum_arrived=85  cum_done=85
RATE arrive=3.76 fps done=3.76 fps dropped_in_win=0 cum_arrived=130 cum_done=130
```

切到「全 NPU」档（**修复前这里就永久停摆**）：

```
GEAR 1 rawlen det=350 rec=344 cls=371
GEAR 1 LOADED det=NNRT:...kirin8020_v2_0 rec=NNRT:...kirin8020_v2_0 cls=CPU
实时识别中 · 全 NPU
丢帧 0 / 100 帧到达          <- 计数在涨，说明循环活着
det  ⚡LANDED=NNRT:NPU_ohos.boot.hardware.kirin8020_v2_0  (req=nnrt)  l2=1110.0817
rec  ⚡LANDED=NNRT:NPU_ohos.boot.hardware.kirin8020_v2_0  (req=nnrt)  l2=4.4338
```

五个档位（生产 / 全 NPU / 全 GPU / 基准 / callback）都能切且持续出帧。

## 落点面板在相机页是实测值

```
det    LANDED=CPU  (req=cpu)  l2=1062.5495
rec  ⚡LANDED=NNRT:NPU_ohos.boot.hardware.kirin8020_v2_0  (req=nnrt)  l2=4.0489
```

`det.l2=1062.5495` 与相册页的 `1076.7692` **不同** → 证明确为实时观测，
不是 UI 复读相册页的值（ADR-0003 的要求）。

## 到达率 ≈ 完成率 ≈ 3.4 fps 的含义

两者相等说明**生产档下流水线比相机出帧快**，这一档测到的是相机侧速率，
不是流水线上限 —— 要测流水线上限得看「全 NPU」档或「基准」档。
「全 NPU」档 `det` 与 `rec` 都在 NPU 上，是回答「榨干 NPU 值不值」的那一格。

## 一条反复出现的模式：**错误信息把真因抹掉**

本轮顺带修掉两个观测缺陷，它们与 T2 的两个「字段名承诺的语义与实际不符」
属同一类 —— **不是崩溃或错值，而是诊断信息本身失真**，于是问题被隐藏得更深：

| 缺陷 | 后果 |
|---|---|
| `ensureSessions` 在 `ctx` 为 `undefined` 时静默 `return false`，而调用方 `applyGear` **无条件**把 status 覆盖成「档位加载失败」 | 现场只剩四个字，拿不到真因 |
| 模型加载失败只记 `LOAD FAIL`，不记各角色的 `ok`/`err` | 无法区分「raw 为空」与「raw 有内容但没有 ok 键」 |
| `totalArrived` 是普通成员却直接渲染在读数卡上 | 「N 帧到达」恒显示 0，看不出循环是否还活着 |

三者都**只能靠观测才能发现**，且都不影响正确性 —— 只影响可诊断性。
本项目已有四处同类（T2 两处 + 此处两处），值得在写新代码时当成一条纪律：
**泛化兜底文案不得覆盖具体原因；渲染到界面的字段必须是 `@State`。**

值得注意的是：如果一开始 `totalArrived` 是正常的 `@State`，
**切档停摆会立刻可见**（「N 帧到达」不再增长），而不必等到发现画面不动。
观测缺陷会掩盖真实缺陷 —— 这是它们比普通 bug 更值得修的原因。

## 一次「修复被静默回滚」的实例（比缺陷本身更值得记）

T8 的提交信息里**明确写了修过这个缺陷**：

> 同时修掉一个真实工程缺陷（首轮 13/51 收到空 KV、native 只见 46 次执行）：
> InferenceRunner 原为单任务槽 + 单一 has_ 标志，并发提交时后者覆盖 task_，
> 而 notify_all 会同时唤醒两者，被覆盖者的 fn 永不执行。改成真正的队列
> （每任务带自己的 finished 标志）。修后干净基线 51/51 完整返回，0 空返回。

这个修复**确实进了 T8 的提交**（`beb92e1` 里 `napi_init.cpp` 是 deque 版），
但在**紧接着的 T7 提交里被整份回滚成旧的 `has_` 版**。blob 逐一对比：

| 提交 | `napi_init.cpp` blob | 形态 |
|---|---|---|
| `ca034a5`（T6） | `81d4a9f6…` | 旧（`has_`） |
| `beb92e1`（T8） | `306beaaf…` | **队列（已修）** |
| `984e3d5` / `6bc6fcb`（T7） | `81d4a9f6…` | **旧（回滚了）** |
| `5731f5a`（本次） | — | 队列（重新修回） |

**机制**：T8 排查那个「未定位异常」时，为了排除自己的改动，检出过
`ca034a5`（T8 之前）的 C++ 去重构建。那个**调试用的检出留在了工作区**，
随后提交 T7 时被一并带了进去 —— `984e3d5` 的 `napi_init.cpp` 与 `ca034a5`
**逐位相同**，正是这条路径的指纹。

于是：相机页从 T7 起就一直坏着，而 T8 的证据（51/51）其实是**在带修复的构建上
采集的**。两者都「为真」，但**从 T7 往后的树无法复现 T8 的 51/51** ——
引用 T8 结果时必须回到 `beb92e1`/`b40cf48`，不能假设 HEAD 还能重现。

**教训（写代码时当纪律）**：

1. **为调试而 `git checkout <旧提交> -- <文件>` 之后，必须显式确认工作区里
   还有哪些「不是我本轮想改的」文件。** `git status` 会把它们列出来，
   但当时只盯着自己的目标文件，就漏掉了。
2. **提交前用 `git diff --stat` 对一眼改动集**。T7 那次改动了两个文件
   （`napi_init.cpp` 与 `Index.ets`），而 T7 的本意只涉及 `Index.ets` 与新增
   的笔记/工具 —— 多出来的那个文件就是回滚。这条只需一秒，能拦住整类事故。
3. **「我记得改过」不能替代按文件确认。** 我先前把这条记成「同一处代码有两份
   实现，所以只修了一份」，那个判断是错的 —— 实际只有一份，而且改过、
   又被自己回滚了。**误判成因会让后续排查完全跑偏**（我为此多花了一轮
   才找到真因）。

## 边界

- 本修复解决「模型加载被丢」，**不解决**相机在暗场景把帧率砍半换曝光
  （30→15）的传感器行为 —— 那是既有结论，与本缺陷无关。
- 3.4 fps 是**当前场景**（室内、暗）的实测值，不是设备上限。
- 一图多牌：相机页实测每帧只有 1 张牌，多牌渲染未验证。
