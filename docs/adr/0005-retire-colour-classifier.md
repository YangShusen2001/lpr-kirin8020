# ADR-0005 · 废弃颜色分类器；标签表确为旋转

- **状态**：已接受（本 ADR 已更正两次，见「更正记录」）
- **日期**：2026-09-20
- **前置**：ADR-0001（继承资产）
- **证据**：理由一用 `_scratch/settle_cls.py`（项目自己的预处理 `encodeClassify`，BGR ÷255）；理由二的重测用 `_scratch/task2_green.py`（**生产路径**：检测 → 透视矫正 → 裁切 → 分类）；`lpr-showcase/assets/js/pipeline.js:35,489,576,621`；`lpr-harmony/.../Index.ets:282-295`；`lpr-showcase/docs/adr/ADR-015`（原为"只登记不裁决"）

## 问题

`lpr-showcase` 遗留一个**未裁决的口径冲突**：颜色分类模型（`litemodel_cls_96x_r1`，1.53 MB，占单帧 2.69 ms / 7.4%）对 `hlpr-test.jpg` 判蓝牌，而牌面像素测量判真绿牌。原项目选择"只登记不裁决"。

该分类器应保留、修复，还是废弃？

## 决策

**废弃。颜色判定改用像素测量（绿色占比 + 色相），零模型开销。**

两条独立理由，**都成立，且是不同的问题**：

### 理由一：项目的标签表是错的（旋转）

源码 `pipeline.js:35` 写 `PLATE_COLOURS = ['yellow', 'blue', 'green']`，`Index.ets:293-295` 镜像为 `0→黄牌, 1→蓝牌, else→绿牌`。

用**项目自己的预处理**（`encodeClassify`：BGR 三平面 ÷255，非 RGB、非 ImageNet 归一化）实测四个**肉眼已核实**的样本：

| 样本 | 肉眼真值 | argmax | 输出 |
|---|---|---|---|
| `crop-0-津B6H920.jpg` | 蓝 | **0** | `0.999946 / 0.000028 / 0.000026` |
| `crop-1-皖KD01833.jpg` | 绿 | **1** | `0.000060 / 0.999850 / 0.000090` |
| `crop-8-冀D5L690.jpg` | 黄 | **2** | `0.000022 / 0.000509 / 0.999469` |
| 1000 张真实集（像素测量判 891 蓝） | 蓝为主 | **0 占 982/1000** | — |

→ **正确顺序是 `['blue', 'green', 'yellow']`。项目表是它的一个旋转。** 按项目表解码，五个已验证样本全部错标。

这解释了原来的"冲突"：分类器的输出索引被**按项目表解码**，于是落到 index 1 的绿牌被读成"蓝牌"。肉眼已核实的绿牌样本 `crop-1-皖KD01833.jpg` 正是 argmax=1。

注意 `hlpr-test.jpg` 在**整图**路径下实测 argmax=**0**（0.99992），不是 index 1；该样本的真值本身仍有争议（见「边界声明」），本 ADR 不以它为旋转证据。

### 理由二（已作废）：原先声称"模型对绿牌不可靠"

**本条理由已于 2026-09-20 第二次更正时删除。** 原结论（`{0: 4, 1: 3}`、仅 3/7 正确、准确率约 43%）是**在错误的输入路径上测出来的**：那段证据用 `_scratch/settle_cls.py` 把**整张场景图**直接喂给分类器，而生产流水线喂的是**检测+透视矫正后的车牌裁切**（`pipeline.js:576` `rotateCrop` → `:621` `encodeClassify(crop)`）。

在**生产路径**上重测（`_scratch/task2_green.py`，检测→矫正→裁切→分类），7 张 CCPD2020 绿牌：

```
argmax 直方图 = {1: 7}      置信度 0.9996–0.9999
```

**7/7 全部落在 index 1**，即修正标签表后的"绿牌"。所以"模型对绿牌不可靠"**不成立**。

两条路径的差异是系统性的，不是噪声：

| 输入 | 绿牌 argmax 直方图 |
|---|---|
| 整图（`settle_cls.py`） | `{0: 4, 1: 3}` |
| 矫正裁切（`task2_green.py`，=生产） | `{1: 7}` |

整图路径把大量车身/背景像素一起送进 96×96，绿牌占比被稀释，因此部分样本落到 index 0。

## 理由（为什么仍要废弃而非修正）

废弃决策**不依赖理由二**，由下列理由独立支撑：

1. **像素测量已能独立判色**：`plate_face_colour.py` 的口径（绿占比 + 色相）在 1000 张上与修正后的分类器一致率约 96.5%，且对 7 张绿牌全部正确。
2. **删掉省 2.69 ms/帧（7.4%）**，像素测量约 0.1 ms。
3. **标签表错误是既成事实**：`pipeline.js:35` 与 `Index.ets:293-295` 的错误表已在生产与端侧镜像，修正需同时改两处并重新验证；而像素测量无查表依赖。
4. **判色是附带属性，不进入识别主链**（见「边界声明」）：为一个非主链属性保留一个 7.4% 帧预算的模型不划算。

## 后果

- 生产流水线从四段变三段：检测 → 透视矫正 → 识别 →（像素判色）。
- `litemodel_cls_96x_r1.onnx` 移出生产路径，仅作论文对照物保留。
- 论文须给出：① 标签表旋转的证据（四样本 + 1000 张直方图）；② 像素测量作为替代口径的验证。
- `lpr-showcase` 的 `pipeline.js:35` 与 `Index.ets:293-295` 的**错误标签表须记录在案**，不得沿用。

## 更正记录

**2026-09-20 首次更正**。初版本 ADR 采信了一个中间结论，称"分类器基本是反的/随机"，并引用了"一致率 1.3%"与"16 种预处理配置最好只有 37.9%"。**该结论与那些数字都是用错误的预处理（RGB / ImageNet 归一化）算出来的**，不是项目实际使用的口径。

用项目自己的 `encodeClassify`（BGR ÷255）重跑后，真实情况是：**标签表旋转（理由一）+ 模型对绿牌不可靠（理由二）**，而非"模型整体失效"。废弃决策不变，但证据与解释已改写。

教训：**复现一个组件的输出前，必须先读它自己的预处理源码**；否则测的是自己的假设，不是被测对象。

**2026-09-20 第二次更正**。首次更正只修好了**预处理**（BGR vs RGB），**没修好输入路径**。理由二用 `settle_cls.py` 把整张场景图喂给分类器，而生产流水线喂的是检测+矫正后的车牌裁切（`pipeline.js:576` → `:621`）。在整图上，"绿牌不可靠"成立；在**生产路径**上不成立（7/7 全对，见理由二）。

因此删除理由二，并撤销其衍生的论文交付项"修正后绿牌准确率仅 3/7"。废弃决策不变——理由一（标签表旋转）与成本理由独立成立。

教训（首次教训的加强版）：**"读被测对象自己的预处理源码"还不够，还要确认喂进去的是不是它在线上的那份输入。** 同一个模型、同一份预处理，喂整图和喂裁切，会给出相反的结论。

## 边界声明

- 绿牌样本 n=7，**统计上很弱**。理由二的原始数字（"约 43%"）已因输入路径错误而撤销，不得引用。
- 像素测量的阈值标定自 1000 张真实集与 7 张 CCPD 绿牌，**极端欠曝/强反光未测**。
- `hlpr-test.jpg` 的真值仍有争议：ADR-015 据像素+几何推定为 8 字符绿牌，而分类器判 index 0。本 ADR **不裁决该样本**，只裁决"分类器不可作为判色依据"。
- 牌色**不进入**识别主链：车牌串由识别器产出，牌色是附带属性。置信度低时应输出"未知"。
