# ADR-0003 · 证据标准 = 延迟差 + 逐算子落点 + 张量指纹；明写利用率不可测

- **状态**：已接受
- **日期**：2026-09-20
- **前置**：ADR-0002（论文主张）
- **证据**：`harmonyos-npu-gpu-squeeze-research.md` §D；`lpr-showcase/_evidence/A17`（`L2asFp16` 列）

## 问题

项目第一目标是"榨干 NPU/CPU/GPU"。但验收标准如果只是"感觉快了"，就无法区分**"模型小所以快"**和**"NPU 真被用上了"**——而后者才是"榨干"的全部意义。

原计划的验收标准是三重证据链：端到端延迟 + **硬件占用证据** + 消融对照表。第二项是否可行？

## 决策

**硬件占用证据这一项，对 NPU 不可行，必须替换。**

文档级结论：**HarmonyOS 上 NPU 利用率无法测量**——应用侧不行，`hdc` 侧也不行（依据见「边界声明」，未对设备做过逆向尝试）。

| 工具 | CPU | GPU | NPU |
|---|---|---|---|
| DevEco Profiler Realtime Monitor | ✅ | ✅ 利用率% | ❌ |
| DevEco Profiler GPU 模板（Studio 6.0.0 Beta3+） | ✅ | ✅ 逐硬件模块计数器 | ❌ |
| SP_daemon（SmartPerf Device CLI） | ✅ | ✅ `-g` 频率+负载 | ❌ 只有 `npu_thermal`（**温度，不是负载**） |
| hidumper | ✅ `--cpuusage/--cpufreq` | ❌ | ❌ |
| hiperf | ✅ 硬件计数器 | ❌ | ❌ |

替换后的验收标准（**三项，缺一不可**）：

1. **延迟差**：同模型、同输入、CPU 与 NPU 两档的 p50 差（warm-up 10 + 100 次取 p50，≥5 轮）。
2. **逐算子落点**：`LANDED=` / `req=` / `fallback=` 三个字段必须能从日志直接读出；Netron 5.1.6+ 打开 `.om` 可看逐算子设备分配。
3. **张量指纹**：NPU 行 `L2asFp16` 非零、CPU 行为 0.0000，证明 NPU 真的算过（而非只返回成功码）。

## 理由

1. **这是平台的真实边界，不是工具没找对**。GPU 利用率可测（SP_daemon `-g` 实测 `gpuFrequency=279000000 / gpuLoad=0.000000`），NPU 只有温度——说明是平台未暴露计数器，不是我们没找到。
2. **`lpr-showcase` 已经在这么做**。它的 `LANDED=` / `fallback=` / `L2asFp16` 三件套正是因为读不到利用率才设计的；ADR-015 明确要求"回落必须在日志里读得出来"。
3. **避免不可证伪的主张**。"NPU 占用 90%"这种说法在鸿蒙上**无法验证**，写进论文是自伤。

## 后果

- 论文与简历中**禁止**出现任何 NPU 利用率数字。允许的表述是"落点"与"延迟差"。
- 任何"NPU 加速 N 倍"的主张必须同时给出：同栈内比值（不跨栈）、热态标注、轮次区间。
- GPU 那一格的口径必须写「通路成立且数值保真」，**不许写「GPU 加速」**——实测三个模型在 Vulkan 上都比 CPU 慢（小图提交开销主导）。

## 边界声明

- 本 ADR 的"不可测"是**基于官方文档与工具清单的结论**，不是对设备做过逆向尝试后的结论。若有人通过 profiler 私有接口或内核态手段拿到 NPU 计数器，本 ADR 应被推翻并新建 ADR。
- `L2asFp16` 是**本项目自创**的指纹口径（按 fp16 重读输出缓冲区），它证明"这个后端算过"，**不**证明"算得对"——正确性仍须靠真值集。
