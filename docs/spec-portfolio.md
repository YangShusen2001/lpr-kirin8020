## Problem Statement

实验阶段已经收口：19 篇实验笔记、6 张图、一份 8 节的英文论文稿、一套 60 项的发布数字守卫、
两个仓库共 0 阻断的合规状态。但**这些成果对外不可用**：

1. **没有入口。** 5 个仓库（`lpr-kirin8020` / `lpr-kirin8020-app` / `lpr-showcase` /
   `lpr-harmony` / `shusen-npu-characterization`）**全部 private**，且没有任何一个 README
   是面向读者的。打开主仓库第一眼是 `CONTEXT.md` 与 ADR。
2. **论文的 GPU 一格只有"实测慢"，没有出处。** 用户明确不接受这个状态——
   「我们真正去搜资料很少，都是自己在埋头苦干，这是非常非常不好的做法」。
3. **RQ4 是单次运行。** "持续负载漂移 26.9%" 随时可能被质疑是噪声。
4. **Related Work 只有 5 篇**，且没有对比基线。
5. **没有任何可交互的演示。** 面试官只能读文字。
6. **没有 NPU 调用指南。** 这一路踩过的坑散落在 19 篇笔记里，对别人不可用。

**目标**：把它变成**能支撑 AI agent 方向求职的作品集**，同时作为毕业设计的专业补充。

**明确不是**：不是投稿。验收标准是"经得起面试官追问"，不是"过同行评议"。

---

## Solution

五件事，按依赖排序：

1. **云手机最小验证**（30 分钟）—— 决定 RQ2（跨 SKU 扩展律）能否复活。
   ADR-0007 当初降级 RQ2 的**唯一理由**是门店演示机不可得；用户现在有云手机资格。
   **这一步可能改论文骨架，所以排第一。**
2. **RQ4 拆两次独立运行**（1 小时）—— 最便宜的严谨性修复。
3. **论文英文稿补完** —— 加 GPU 章节（已有官方出处）、扩 Related Work 到 15–25 篇、
   尝试基线对比、逐表补「框架」列。
4. **NPU 调用指南（中文）** —— 按"你会踩的坑"组织，每条含可复现的最小验证。
5. **鸿蒙 App 重设计 + 演示页改造 + 展示页** —— 骨架先行（色块占位），再填真实数据。

**贯穿纪律**：**先搜一手资料，再动手实测。** 两者并行，不是后者替代前者。

## User Stories

### 面试官（首要读者）

1. 作为面试官，我想在 30 秒内知道这个项目**解决了什么问题**，这样我不用读长文。
2. 作为面试官，我想**自己上传一张车牌照片**就看到结果，这样我不必相信一段录屏。
3. 作为面试官，我想看到**一个数字对应的证据文件**，这样我能验证它是不是编的。
4. 作为面试官，我想知道**作者推翻过自己几次、怎么推翻的**，这样我能判断他的严谨性。
5. 作为面试官，我想在 40 秒内看完演示，这样我不会中途走开。

### 其他开发者（次要读者）

6. 作为鸿蒙开发者，我想知道**怎么正确调用麒麟 NPU**，这样我不用重复踩坑。
7. 作为鸿蒙开发者，我想知道**哪些坑会导致静默失败**（`-O0` 覆盖 `-O3`、非 ASCII 路径、
   FULL_QUANT 整图回退），这样我能及早发现。
8. 作为开发者，我想知道**GPU 在这台机器上到底能不能用于推理**，这样我不浪费时间。

### 未来的自己

9. 作为作者，我想让**每个对外数字都可机检**，这样我改证据后不会忘记改文档。
10. 作为作者，我想让**继承来的数字与新增数字分开标注**，这样不会重复计数。
11. 作为作者，我想让**负结果也落盘**，这样下一轮不会重试同一件事。

### 研究者（云手机验证）

12. 作为研究者，我想知道**云手机能否用于采性能数据**（thermal 可读？Vulkan 是否虚拟化？），
    这样我决定 RQ2 要不要做。

### 鸿蒙 App（6 块组件，不再增加）

| 区块 | 组件 |

### 演示

- 演示页**改造** `lpr-showcase/index.html` / `demo.html` / `mobile.html`（现有成品，
  纯前端、零网络请求），不重做。
- 嵌入可点击的手机样式容器。
- **三个场景共 40 秒**：
  1. 传图 → 出结果（10 s）
  2. 切换后端 CPU ↔ NPU → 看落点与延迟变化（20 s）
  3. 打开落点自证面板 → 看分段耗时（10 s）

### 展示页

求职叙事定位。每个项目 **5 个字段**：
一句话主张 / 三个数字 / 技术栈 / 状态（完成·进行中）/ 链接。

**不放**「是否对求职有帮助」——那是内部筛选判据，不是访客需要的。

### AI agent 叙事的落点

- **桥** = **发布守卫机制**（`tools/verify_published_numbers.py`）：
  「声明值必须能被机检重算，对不上就拒绝发布」。这是 agent 自我纠偏的可落地形态。
- **证据** = **自我更正时间线**（T10→T12、T11→T14、ADR-0003/0005 更正）。

## Testing Decisions

**什么算好验收**：只测**外部可观察**的东西，不测实现细节。

| 工件 | 验收方式 |
|---|---|
| 论文 / README / 展示页的数字 | `tools/verify_published_numbers.py` 全通过（当前 60 项） |
| 对外仓库 | `tools/scan_for_publication.py` **0 阻断** |
| 演示页 | 面试官能**自己上传一张车牌照片**看到结果（不是录屏） |
| 鸿蒙 App | 主界面能在 30 秒内演示完三个场景；探针控制台不出现在主界面 |
| NPU 指南 | 每条坑都有一个**可执行的最小验证脚本或命令** |
| 云手机验证 | 三个问题都有确定答案（能装 / thermal 可读 / Vulkan 是否虚拟化） |
| RQ4 拆分 | 给出两次运行的漂移量；**若第二次不复现，如实写"未复现"** |

**不测**（交人工）：UI 观感、演示页的视觉、论文的可读性。

## Out of Scope

- **投稿**（含 arXiv 预印本）—— 本轮不做，未来可选
- **中文论文** —— 论文只出英文版
- **产品级 UI** —— 用户原话：「不需要设计成产品的这么高规格，只需要简单清晰、实看」
- **红果短剧 / 抖音 / 快手自动化** —— **下一个项目**，本轮只在展示页登记为"进行中"
- **Browser Use + Jev** —— 同上方向。最小原型已设计（[`notes/on-device-decision-model-survey.md`](notes/on-device-decision-model-survey.md) 附录二）
- **麒麟 9050 / 云手机全系列测试** —— 待云手机验证后再规划
- **融合携带「相关 → 因果」** —— P3，等审稿意见或作为未来工作
- **双层黄牌 / 港澳两地牌** —— 如实写"未测"即可
- **HiAI Foundation 的 GPU 算子** —— 待验证，优先级低（即使开放也不改变"GPU 不如 CPU"）

## Further Notes

### 本轮 grill + research 的三条关键产出

1. **GPU 结论被升级**：从「我们测出来慢」到「官方没提供这条路」
   （CANN/NNRt/MSLite 的计算单元清单无 GPU；MS Lite 的 GPU 回落是平台设计；
   ncnn 官方 FAQ 自陈 ARM 手机 GPU 慢于 CPU 是常态）。
2. **Jev 的瓶颈判断被纠正**：OSWorld-Human 实测规划+反思占 87–97%，
   **截图与动作只占 1.1–3.3%** —— 该优化的是"减少调用次数 + 压缩上下文"。
   另：Jev 无视觉；**HarmonyOS 手机端 Computer Use 方向不成立**
   （无障碍 API 自 12 起全部 deprecated 且无三方替代）。
3. **语言分工被纠正一次**：外推范围越大，越要回问。
