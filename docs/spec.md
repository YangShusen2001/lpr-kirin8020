## Problem Statement

想在麒麟 8020 上跑端侧车牌识别的人，面对的是一个**看起来能用、但说不清为什么**的平台：

- 同一个模型请求 NPU，有时真的落在 NPU、有时**静默回落 CPU**，日志里不写；
- 落了 NPU 也不一定快——实测加速比从 **13.11× 一路掉到 0.98×**，小图甚至负收益；
- 有些模型在 NPU 上**算错**（检测器把 `苏ED5172` 读成 `苏E05172`），但没有任何错误码；
- 想证明"NPU 真的被用上了"，却发现**平台根本不暴露 NPU 利用率**——应用侧不行，`hdc` 侧也不行。

结果是：没人能给出一条"什么模型该放哪个后端"的**可判定规则**，只能靠试。而试错的代价很高——每个模型要转换、装机、跑 5 轮协议、标热态。

同时，官方文档与实际能力存在**两处系统性偏差**，会让开发者白走很远的弯路：

- MindSpore Lite 官方算子表里，**198 个算子只有 58 个有 Kirin NPU 实现，且全部 FP16-only**；`LayerNormFusion` / `EmbeddingLookupFusion` 等**完全没有**——但文档不会告诉你"所以 transformer 上不去"。
- 一份**预训练模型在真实分布上失效**（颜色分类器），却被当作"第二种意见"引用，导致一个未裁决的口径冲突挂了很久。

## Solution

交付一个**可复现的端侧车牌识别 App**，它同时是一台**测量仪器**：每一次推理都把「落在哪、花了多久、算子怎么切」写进日志，让结论从原始数据直接读出来，不需要读者相信一句断言。

三条支柱：

1. **落点自证**：每次运行输出 `req=`（请求的后端）/ `LANDED=`（实际落点）/ `fallback=`（是否回落），加张量指纹（`L2asFp16` 非零 = NPU 真的算过）。**这是平台上唯一诚实的证据形态**，因为利用率不可读（ADR-0003）。
2. **算子覆盖边界**：用「独立委托 vs 融合携带」模型解释为什么某些算子单独构图被拒、却能作为 Conv 的融合邻居上 NPU。据此给出**可预先计算**的选型判据（`Cin`/`Cout` 双 16 倍数占比），并用 CANN 的 166 个 IR 算子做对照面。
3. **纠正文档与模型的两处偏差**：把官方算子表的实际覆盖边界量化；把颜色分类器的标签表旋转**裁决**掉，换成像素测量。

以中文车牌识别四级流水线（检测 → 透视矫正 → 识别 → 判色）为应用级案例（RQ3），并测持续负载热特性（RQ4）。

## User Stories

### 识别能力

1. 作为用户，我想导入一张相册照片就得到车牌串，这样我不用联网也不用等。
2. 作为用户，我想用相机对准车辆实时看到车牌串叠加在画面上，这样我不用先拍照再选图。
3. 作为用户，我想看到每块车牌的检测框与置信度，这样我能判断结果可不可信。
4. 作为用户，我想支持**蓝牌**与**绿牌新能源（8 位）**，这样路上最常见的两类车都能识别。
5. 作为用户，我想在识别失败时看到"未检出"而不是一个编造的结果，这样我不会被误导。
6. 作为用户，我想看到牌色判定结果，这样我能区分燃油车与新能源车。
7. 作为用户，我想在牌色置信度低时看到"未知"而不是猜测，这样我不会被误导。
8. 作为用户，我想支持一图多牌（多辆车同框），这样路口/停车场照片也能用。
9. 作为用户，我想在无网络环境下完整使用，这样地下车库也能用。
10. 作为用户，我不想被要求授予通讯录/位置等无关权限，这样我放心安装。

## Implementation Decisions

### 架构

- **单后端**：App 只用 MindSpore Lite + NNRT（ADR-0004）。理由：实测 CANN 在三个模型上都不比 MS Lite 快（rec 5.19 vs 3.99 ms），且 A10 已证明 MS Lite 的 NNRT delegate **就是官方 NNRt 底座**（设备名逐字互证）。
- **native C++ 核心 + ArkTS 外壳**：推理框架只有 C/C++ API，纯 ArkTS 走不通。NAPI 暴露流水线。
- **会话常驻**：NNRT delegate 析构路径存在 cppcrash，模型会话在应用生命周期内复用、不重建。
- **固定 batch = 1**：带动态 batch 维度在 `OH_AI_ModelBuildFromFile` 阶段直接失败。
- **判色改为像素测量**（ADR-0005）：删除颜色分类模型，改用绿色占比 + 色相。省 2.69 ms/帧。

### 模块

- **流水线核心**：letterbox → 检测 → NMS → 透视矫正 → 识别 → 判色。返回每块车牌的框、字符、逐字符概率、分段计时。
- **引擎层**：模型加载 / 推理 / 落点记录 / 性能模式。**必须记录 `req=` 与 `fallback=`**——`LANDED=CPU` 本身分不清"我们选的"还是"回落的"。
- **落点面板**：把落点、分段预算、张量指纹呈现出来，可导出 JSON。
- **像素判色**：从矫正后的车牌裁剪采样，输出牌色 + 置信度（低则"未知"）。
- **算子探针**（论文用，不进 App）：逐算子模型 + 后端对撞。

### 接口契约（落点面板返回结构）

决策要点：落点与分段计时**必须与识别结果同一次调用返回**，否则两者对不上帧。

```
{
  plates: [ { rect, detScore, layer, code, recConf, chars, charProbs,
              colour, colourConfidence, cropSum } ],
  stages: { letterboxMs, packMs, inferMs, decodeNmsMs, rectifyMs, recogMs, colourMs },
  backends: [ { role, req, landed, fallback, tensorFingerprint } ],
  thermal: { level, batteryTempC, charging }
}
```

- `landed` 是**观测值**，`req` 是请求值；两者不同即发生回落。
- `tensorFingerprint` 为 NPU 行非零、CPU 行为 0，用于证明 NPU 真的算过。
- `cropSum` 保留为跨实现指纹（前期工程的既有口径，逐位可比）。

### 必须修正的既有缺陷

- `lpr_pipeline.h` 中 `float cls[3]` 的注释写的是 `yellow, blue, green`——**这是旋转的错误标签表**。ADR-0005 实测正确顺序为 `blue, green, yellow`（肉眼核实：蓝→0、绿→1、黄→2；1000 张真实集 index 0 占 982）。新实现不得沿用该注释。
- 前期工程的 `PLATE_COLOURS`（`pipeline.js:35`）与 `Index.ets:293-295` 同为此错误，**记录在案，不得继承**。

### 转换链（模型不入库）

- `.ms`：`converter_lite.exe` 2.6.0，PC 端，**无需华为账号**。三个模型已实测转换成功且 SHA256 与前期工程一致。
- `.om`：CANN DDK 的 OMG，**必须用包装脚本**而非 `master/omg`；**输出路径不能含非 ASCII 字符**；不要传 `--target=omc`（会产出 `.omc` 而非 `.om` 且 `rc=0` 静默成功）；版本参数是 `--hiai_version` 不是 `--omg_version`。已在 WSL 实测复现（[notes/toolchain-and-sources-on-disk](notes/toolchain-and-sources-on-disk.md)）。

### 数据

- 精度评估**只用带人工真值的集**。前期工程 `_dataset/real/crops`（n=1000，文件名即真值）作基线，但须同时报告其省份分布（**956/1000 是皖**）。
- 省份均衡用**公开集零星抽取**补齐：`richjjj/chinese_license_plate_rec` 的 `val/data.mdb`（17.8 MiB 下载 → 按省份抽 15 张/省 → 280 张 / 26 省 / 2.22 MB）。实测可行。
- **不训练任何模型**。多牌型是**验证任务**（ADR-0006）：现成识别器已实测能读 8 位绿牌（7/7，conf 0.9897–0.9998）。

## Testing Decisions

### 什么算好测试

只测**外部行为**，不测实现细节。对本项目具体化为：

- **落点必须从返回值直接读出**，不接受"请求了 NPU 就算成功"。
- **分段计时之和应≈端到端**（允许小残差），否则说明有未计时路径。
- **同一输入两次运行结果逐位一致**（`cropSum` 不变），否则说明有未初始化的状态。
- 精度测试**只引带人工真值的集**；参照串只作跨实现对齐锚点，**不构成正确性证据**。

### 测试缝（已与用户确认）

**主缝（唯一必需的新缝）**：native 流水线的 **NAPI 边界**。

```
pipeline(rgbaBuffer, width, height) → { plates, stages, backends, thermal }
```

一条调用覆盖四段流水线；落点、分段计时、张量指纹都在返回结构里，可断言。**这是最高缝**——再往上只有相机与 UI，它们不可无头测试。

**复用缝（不新增）**：

- **转换脚本级**：断言"重跑 → 字节数与既有产物一致"（`.ms` 已验 SHA256 一致；`.om` 已验字节数一致）。不需要新缝。
- **离线跑分（文件驱动）**：精度评估不进 App，用目录扫描 + 真值文件名比对。已有先例（前期工程 `tools/lprnet_real_accuracy.py`）。

### 被测模块

| 模块 | 测什么 | 缝 |
|---|---|---|
| 流水线核心 | 给定固定 RGBA 输入 → 车牌串/框/分段计时 | NAPI 边界 |
| 引擎层落点 | `req` vs `landed` vs `fallback` 三个字段的一致性 | NAPI 边界（返回结构内） |
| 像素判色 | 已知牌色样本 → 正确牌色；低置信度 → "未知" | NAPI 边界 |
| 转换链 | 重跑产物与既有产物一致 | 脚本级 |
| 精度 | n=1000 基线 + 省份均衡集 + 绿牌子集 | 离线跑分 |

### 不测（交人工，`ready-for-human`）

- **相机实时**：无头测试测不了相机与叠加层。
- **热行为（RQ4）**：需真机连续 20 分钟，且需人工确认热档。
- **真机 `.om` 三关**（`compat`/`build_rc`/`run_rc`）：需设备解锁。
- **UI 交互**：人工验收。

### 先例

- 前期工程已有 NAPI 探针（`pipeline` / `bench` / `listNnrtDevices` / `vulkanProbe`），返回 KV 字符串。新实现沿用其**字段语义**（`LANDED=` / `req=` / `fallback=` / `L2asFp16` / `cropSum`），但改为结构化返回。
- 前期工程的 `A18 §8` 已建立"分段计时"的字段名与 9 段口径，直接沿用。

## Out of Scope

- **RQ2 跨 SKU 扩展律**（9010/9020/9030）：依赖门店演示机，渠道不可控，降级为未来工作（ADR-0007）。
- **端侧 LLM**：CANN LLM Engine 的 31 个符号全部 `deviceType=0100000` = **仅 2in1**，**全手机不可用**（X90 也不行）。三条闸门独立成立。已证伪，不投入。
- **自动化操作其他应用**（如自动点金币）：设备侧注入点击三堵墙（系统接口 / PC-2in1 限定 / 无障碍 API 12 起废弃），**纯手机不可实现**（[notes/unattended-automation-on-device](notes/unattended-automation-on-device.md)）。搁置。
- **训练或微调任何模型**：硬约束。
- **多摄并发**：硬件与平台均不支持。
- **GPU 加速叙事**：实测三个模型在 Vulkan 上都比 CPU 慢（小图提交开销主导）。GPU 那格只能写"通路成立且数值保真"，**不许写"GPU 加速"**。
- **NPU 利用率数字**：物理上不可读（ADR-0003）。

**继承时须复核**：`ShusenPaper` 的 checksum 校验发现过两处 FAIL（`native_decode_tail`、`yolov8n` 原版），复用前确认所用子集已通过校验。

### 两处已知的文档/模型偏差（本项目的贡献之一）

1. **官方算子表 vs 实际能力**：MindSpore Lite 官方表 198 算子中仅 58 个有 Kirin NPU 实现，**全部 FP16-only**；`LayerNormFusion` / `EmbeddingLookupFusion` / `Erf` / `RealDiv` / `Shape` **完全没有**。后果：attention 的 matmul 可以，但**碰到 LayerNorm 或 embedding 表就掉出 NPU**——这是 transformer 上不去的结构性原因。
2. **预训练模型的标签表与项目解码不一致**：颜色分类器标签表旋转（正确顺序应为 `blue, green, yellow`，项目表是它的一个旋转），按项目表解码会把绿牌读成蓝牌。ADR-0005 已裁决改用像素测量。

### 诚实边界（必须随结论一起说）

- `L2asFp16` 指纹证明"这个后端算过"，**不证明"算得对"**——正确性仍须靠真值集。
- 前期工程 90.6% 的精度建立在 **956/1000 皖**的集上，84 个同长度替换错误里 **78 个发生在省份位**。**省份泛化从未被测过**，本 spec 的均衡集就是为补这个缺口。
- 绿牌 7/7 的**长度**（8 字符）是硬证据（读自 CCPD 文件名），**具体字符**依赖标准 CCPD 字典（属推断）。
- 算子覆盖矩阵是 **NNRT 通路**的；CANN 的 166 个 IR 算子是**文档级**证据，尚未在本设备逐算子实测。
- `hdc shell param get const.hiai.vendor.hiaiversion` 在 USB 连接的非 2in1 设备上返回 `errNum 1002`（参数不存在）——版本对齐只能走应用内 API。

### 硬约束速查

1. NPU 利用率不可测 → 禁止任何利用率数字。
2. 会话必须常驻（析构会 cppcrash）。
3. 固定 batch = 1。
4. 改端侧代码前先干跑编译（`lpr_pipeline.cpp.yolov8_backup` 与 `lpr_pipeline_new_v2.cpp` 是遗留物）。
5. OMG 输出路径不能含非 ASCII 字符。
6. 持续后台计算不被允许（`SystemLoadLevel` 8 档，HIGH(3) 起停无感服务）。
